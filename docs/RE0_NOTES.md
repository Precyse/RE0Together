# RE0 HD Remaster: reverse-engineering notes

Build: Steam app 339340, buildid 17178773, `re0hd.exe` 32-bit, image base 0x400000, **no ASLR** (addresses below are absolute). SteamStub-wrapped: `.text` is encrypted on disk and decrypted in memory before the game's own code runs. Adapter hooks must wait for decryption. Found with `tools/re0/probe.py` and `tools/re0/disasm.py` (runtime reads only).

## MT Framework type info
- Every class vtable slot 4 is `getDTI()` = `mov eax, <dti>; ret`. The DTI's field +4 is the class-name string.

## Globals (pointer to singleton)
| address | singleton |
|---|---|
| 0xdcbf3c | sPlayer* |
| 0xdcc0d0 | sGameChara* |

## sPlayer
| offset | meaning |
|---|---|
| +0x2c | controlled character (uPlayerBase*) |
| +0x3c | partner character (uPlayerBase*) |

The V key (partner switch) swaps +0x2c/+0x3c. sGameChara mirrors them at +0x148c/+0x149c.

## uPlayerBase (uPlayerBilly / uPlayerRebecca), about 0x6AD0 bytes
| offset | meaning |
|---|---|
| +0x40 | position vec3 (+pad) |
| +0x50 | rotation quaternion xyzw |
| +0x60 | scale vec3 |
| +0x70 | world matrix 4x4 (current); +0xB0 previous |
| +0x498, +0x4a0 + n*0x140 | motion state (static study 2026-10-19, "Pose puppet" below): +0x498 `mMotionCalcFlag`, `mMotion[8]` layers of 0x140 bytes; per layer +4 u16 motion number (bank in bits 8..11, 0xffff = none; layer 0 = +0x4a4), +0x40 `mInterFrame` (blend length in frames: the earlier "+0x4e0 float 8.0 idle / 6.0 walking" was this, not a frame), +0x4c **current frame** (layer 0 = +0x4ec, advanced each update), +0x54 frame max (+0x4f4), +0x5c speed (+0x4fc). +0xff8 `cAnimControl`, +0x6a70 byte "keep the motion's own displacement" |
| +0x67b8 | think (brain) object: cPlayerThink (vtable 0xccbbe8) when controlled, cPlayerSubThink (vtable 0xcc99b8) when partner. V swaps them. Setter at 0x508b1e |

## Think (brain) interface
- Slot 20 (+0x50) = which pad to read. cPlayerThink 0x4f9f10 → `sGamePad::getPad(0)`; cPlayerSubThink 0x4f4be0 → `getPad(1)` (the partner's arrow-key pad).
- `sGamePad::getPad(i)` at 0x600630 (thiscall, 1 stack arg, i < 2) returns the pointer at `sGamePad + 0xc24 + i*8`, or 0 while input is blocked.
- Player code calls think slots +0x1c, +0x20, +0x28, +0x38 on the character's think. +0x38 is a target-eligibility filter (loop of ≤ 20), not input.

## Think lifecycle (confirmed)
- `sPlayer::setControlled(player)` 0x4ecda0: `alloc(0xd0, 0x10)` (cdecl 0x4f81e0), `cPlayerThink` ctor 0x4f8010 (thiscall, returns this), `player->setThink(t)` 0x50f980 (thiscall, ret 4, destroys the old think), `sPlayer+0x2c = player`.
- `sPlayer::setPartner(player)` 0x4ece00: same flow with `cPlayerSubThink` (alloc 0x4f3760 size 0x1a0, ctor 0x4f3540), `sPlayer+0x3c = player`.
- V recreates both thinks; it does not swap objects.
- cPlayerThink DTI 0xdcebac. DTI vtable slot 1 = newInstance.

## Per-frame (tracer, 60 fps)
- `uPlayerBase::move` 0x513190 (thiscall, no args), vtable slot 41 (Billy reaches it through a wrapper at 0x51b683). It calls think slots 5, 6, 16, 21, 25 once per frame.
- cPlayerThink calls its getPad (slot 20) about 12x/frame, e.g. 0x4fa420: `pad = think->getPad(); return pad->vfunc[9]() == 1`.

## Pad object (vtable 0xce55e0, 36 slots)
- Slots 5..35 are action queries forwarding to two inner devices at +4 and +8 (keyboard/joypad), OR'ed. Most return bool.
- Slot 14 returns a struct via hidden out-pointer (`ret 4`), probably an analog vector.
- Slots 8/9/14/15 first check `sGamePad+0xbcd` and `0x5fe490(this+8)`.
- **Network pad plan:** an object with a copied vtable whose slots 5..35 return the remote player's recorded answers. The partner's cPlayerThink gets it via its getPad (slot 20).

## Co-op control model (decided 2026-09-29, revised)
- Fixed ownership: the host always owns Rebecca and the first peer always owns Billy, whoever is focused. Each machine always keeps its own character focused (camera_parity, in Team and Split up alike; V/Y do nothing with a peer): the party mode only decides door travel.
- Control rule (`character_owner::controlOf`, pure part in `control_rule.h`): no peer is vanilla; an unknown owner is vanilla on the host and Locked on a guest; both characters stay with their owners (Local or Remote) in both party modes; a Remote character is Locked while its owner reports another room than the one loaded here (its input belongs to that room). TEAM = following and doors together; LEAVE_BEHIND = independent play (nobody follows). The camera is per machine in both. Damage, inventory and state sync follow ownership only (`isRemoteOwned`/`isLocalOwned`).
- PLAYER_STATE (44 bytes) describes the sender's owned character (position, hp, characterId), whatever the camera is on; `focusedCharacterId` (the camera character) is diagnostic only.
- Menus: menu_mirror focuses the own character for the menu and camera_parity keeps it afterwards.
- Party commands are adapter-level because the game reads V/E from the focused character's think, whose input on a non-owner's machine is the remote pad. `command_input` polls KC_change (V) and KC_trace (E) from `%LOCALAPPDATA%\CAPCOM\RESIDENT EVIL 0 HD REMASTER\config.ini` from the game's own input (see "Command input source" below). V/Y are only hidden from the game (SWITCH_REQUEST 0x0103 is gone; each player keeps their own camera). E toggles the party mode: PARTY_REQUEST 0x0109 to the host, which flips and broadcasts PARTY_MODE 0x010A (reliable, also every 2 s); toasts "Team" / "Leave behind: <character> waits". The vanilla E toggles sPlayer +0x40 (u8, 1 = partner follows); party_mode now owns that byte while a peer is connected.
- Vanilla camera model: both clients keep the same controlled character (sPlayer+0x2c) and show the same room. The owner of each character drives it with their pad; the other client replays that input.
- If the partner is in another room it idles as in vanilla. Split-room simulation is deferred (too much data).
- The V switch changes the active character. Only the owner ever drives a character.
- One PC cannot run two RE0 instances: SteamStub ends the second one. Testing uses the echo peer, and real tests need two Steam accounts that each own RE0.

## Proven in-game (2026-09-29)
- Giving the partner a cPlayerThink (alloc + ctor + setThink) is stable, and the partner then obeys the pad exactly like the controlled character (identical 90° turn, both walk). **Co-op strategy: the remote player drives the partner via input replay; state sync only corrects drift.**

- **Network input replay works end to end** (echo test, 1 s delay): the partner reproduces the sender's turns and walks with native animation; drift snaps are rare.
- `getPad` returns a dummy pad (`sGamePad+0xc34`, vtable 0xce58b8) while input is blocked; only vtable 0xce55e0 objects are real pads.
- The joypad's stick query (slot 14) writes its out-vector with `movaps`, so the buffer must be 16-byte aligned.

## Enemies (found 2026-09-29, hardware write breakpoint via tools/re0/watch_write.py)
- Classes uEnemyNN, object about 0x6cc0 bytes, same transform layout as players (+0x40 pos, +0x50 quat).
- **HP: i32 at +0x1030** (fresh uEnemy11/12/16 = 94, handgun hit = 16). Dead enemies hold -1, re-written every frame by their update (0x526c7d → 0x42105d → 0x41eb60 → 0x424a2a).
- `setHP(this, i32)` 0x529310 (thiscall, ret 4). It is called by per-class code.
- **Damage entry: enemy vtable slot 35 (+0x8c)**, `damage(attacker, HitPoint*, HitInfo*)` thiscall ret 0xC. uEnemy11 implements it at 0x4200c0. The second argument is a pointer to the world-space hit point (3 floats), not a distance (corrected 2026-10-07, see "Hit point" below).
- Hit resolver 0x5313b0 (ret 0x18) builds `HitInfo { i32 rangeTier; i32 attackType; i32 a; i32 b; void* attacker; u8 flag }` and calls slot 35. rangeTier 0..3 comes from distance thresholds. attackType 0x1b takes a special path through sPlayer (0x4eca10). Caller chain: 0x7d4d20 → 0x542710 → 0x52f520 → 0x5313b0.
- **sEnemy\*** global at 0xdcdc78. Its enemy pool is at sEnemy+0x4b0: 16-byte entries `{vtable 0xcbd01c, next, prev, uEnemy*}`, 37 slots (+0x4a8 = 0x25). **Pool slot index = enemy network id** (same save and room means the same spawn order).
- The 38 enemy class vtables (slot 35 = damage; 18 distinct implementations): 0xcbdcd8, 0xcc4f28, 0xcc50a0, 0xcc5218, 0xcc5390, 0xcc5508, 0xcc5680, 0xcc57f8, 0xcc5970, 0xcc3fe8, 0xcbf0d0, 0xcbf5f8, 0xcbf9a0, 0xcbfbc8, 0xcbfe58, 0xcc01a8, 0xcc0458, 0xcc08c0, 0xcc5ae8, 0xcc0cb0, 0xcc13d8, 0xcc1618, 0xcc18e8, 0xcc5c60, 0xcc1ce8, 0xcc1e60, 0xcc1fd8, 0xcc25d8, 0xcc2b38, 0xcc2f70, 0xcc3248, 0xcc3710, 0xcc5dd8, 0xcc5f50, 0xcc60c8, 0xcc6240, 0xcc63b8, 0xcc6530.
- Co-op plan: the guest sends {enemy id, attackType, a, b, rangeTier, hit point, attacker character}. The host calls slot 35 with its own object for that character. Still open: a stable enemy id (index in sEnemy's list), and enemy state replication to the guest.
- Player damage: player HP is i32 at +0x1030 (Rebecca 150, Billy 161 seen), set with the same setHP 0x529310. `uPlayerBase::takeDamage(a, b)` 0x50fb30 (thiscall, 2 stack args, ret 8) is called from the player's own update, takes the amount from sEnemy 0x416de0 and floors HP at 1. Enemies also call it from their own update (0x76f9e8 → 0x5127c5).
- **Player hits (damage and death):** the earlier reading that every hit goes through vtable slot 38 0x512080 as `processHits` is wrong (corrected 2026-10-19): 0x512080 is a reset / re-entry (it calls `Player_Reset` 0x516440, changeState(0, 0, 1), think slot 6 and the ground snap; `setWeaponType` calls it) and nothing hooks it. Enemy hits and grabs enter through slot 34 0x512570 ("Pose puppet" below). Normal hits call takeDamage. The lethal hit calls think slot 6 → 0x4fcea0 (cPlayerThink slot 28) → 0x4fd010, which does setHP(0). The adapter gates setHP and onDeath for a remote-owned character (`player_damage`), and PLAYER_STATE carries the owner's HP.
- Ownership gate (2026-09-29): damage also reaches players through queued damage in their own update (0x513570 → 0x4fd160 → takeDamage) and the lethal hit (think->changeState 0x4fb2a0 → cPlayerThink slot 28 `onDeath(player)` 0x4fcea0 → killPlayer 0x4fd010 → setHP 0). So the adapter gates **setHP** (remote-owned players ignore non-authoritative writes) and **onDeath** (skipped for remote-owned characters; the owner sends PLAYER_DIED 0x0120 and the other machine replays onDeath). The partner's cPlayerThink is allocated at 0x1a0 and zero-filled.
- Crash 2026-09-29: heap corruption (0xc0000374) when the echo-driven partner Billy "died"; root cause not confirmed.

## Rooms, doors, menus, saves (2026-09-29)
- **Door entry point:** every door calls `sRoomControl::changeRoom(room, entry, flags)` at 0x610c60 (thiscall on sRoomControl 0xdcbeb4, ret 0xC; the only caller is the door thunk 0x552720, flags 0x20001, room/entry from the door object +0x20/+0x24). It calls 0x61e2c0 on sSceneInfo (0xdcbf40), which carries the partner (sPlayer +0x3c) along when sPlayer +0x40 (follow) is set and partner +0xff4 equals the scene's current room record (sSceneInfo-side +0x20; record +8 = room id). The carry repositions the partner (writes at 0x61edcb / 0x61b321) and does not change partner +0xc or +0xff4 (+0xff4 is the same object in both rooms). Writing +0xff4/position by hand leaves the game half-updated (E refused, crash on the partner's next door).
- **Story flags:** sFlagManager (global 0xdcc014, size 0x144, vtable 0xcd9184, DTI 0xdcff60) holds the script flags as 0x47 dwords at +0x20. Script opcodes (table of 12-byte rows {handler, signature, name} from 0xcd57d8; corrected 2026-10-07, the rows were read one field off before, see "Room script events"): FlagSet 0x577790 calls set(index, value) 0x59bd50; FlagSetMB 0x577830 calls set(index, count, value) 0x59c980 (thiscall, ret 0xC); FlagSetF 0x5778d0 goes through 0x59c960; SetLocalFlag 0x577f50 uses the singleton at 0xdcbebc. flag_sync diffs the 0x47 words (FLAG_DIFF 0x010C).

All script flag families share that bitset. Each setter adds its operand to a base: story 0x000 (FlagSet), enemy 0x312 (SetEnemyFlag 0x577970 through 0x59c320), effect 0x412 (SetEffectFlag 0x577c00), act 0x612 (SetActFlag 0x577ac0), display 0x712 (SetDisplayFlag 0x571710), bgm 0x812 (SetBGMFlag 0x577dc0). Bit n is `(sFlagManager + 0x20)[n >> 5] >> (n & 31)` (getter 0x59b8d0). The generic setter 0x59bd50 (set(index, value), thiscall, ret 8) writes the bit, then runs per-family side effects: enemy bits 0x312..0x411 (spawn/clear through 0x61a2b0, 0x4109f0, 0x411ec0, 0x619e30), effect bits 0x412..0x611 (0x560720/0x560740 when set, 0x55d9e0/0x55da00 when cleared), display bits 0x712..0x811 (0x59b6a0). Act and bgm bits are plain bit writes there; the BGM wrapper SetBGMFlag 0x577dc0 calls the BGM refresh 0x643490 when the value changes. Per-flag table with the rooms that set and read each one: docs/re/RE0_FLAGS.md; the classifier is adapters/re0/src/flag_family.h.
- **Room phases:** sRoomControl (0xdcbeb4) +0xb8 is the phase manager (vtable 0xce6bdc): +0x8 count 0x18, +0xc array of phase objects, +0x14 current, +0x18 requested (-1 none), request(phase) 0x60a340 (thiscall, ret 4; sRoomControl::requestPhase 0x610e00 adds 0xb8). Index: 0 Init, 1 Main, 2 Message, 3 MessageImm, 4 DoorLoad, 5 SubScreen, 6 Save, 7 UpCut, 8 Option, 9 Change, 10 EventDemo, 11 Map, 12 Movie, 13 Event, 14 Dead, 15 Opening, 16 StaffRoll, 17 Ranking, 18 WeskerTitle, 19 WeskerRanking, 20 OmakeTitle, 21 OmakeResult, 22 PlayDemo, 23 Exit (read from the live array, 2026-09-29). Class vtables: cRoomPhaseMain 0xce6b90, Dead 0xce68a8, EventDemo 0xce6a20, Movie 0xce6ea0.
- **Zapping (V):** the vanilla V requests room phase Change (9) through sRoomControl::requestPhase 0x610e00 from the player think (0x4fed48 when the target is the partner, 0x50395e); the Change phase does the swap and loads the partner's room when apart. camera_parity swaps directly in the same room and requests Change when the partner is in another room (untested in game).
- **Save manager / slots:** singleton 0xdcc018 (+0x20 request object; dispatch 0x6133d0 on op +4: 1 0x612ad0, 2 0x612c40, 3/4 0x613080 load, 5 0x612e30, 6 0x612d20). Load request (slot, 0) thiscall ret 8: op 3 0x6134c0, op 4 0x613500 (the load menu calls them through 0x613cb0/0x613cc0 with its cursor index); save request (slot) ret 4: op 5 0x613390 (via 0x613c40, called from the save GUI). Slots 0..19 are player saves; slot 21 (0x15) is the system data read at boot ("Load successful."). From boot, Enter on every screen reaches the game through the notice, title (Load Game default), load list and Continue.
- **Game over:** Main -> Dead (14) phase; uGUIGameOver vtable 0xcdb2f0, sGameOver 0xcdb288. Setting HP to 0 does not kill; death only comes through the damage path. Writing the phase manager's request field directly crashed the game (use requestPhase). The co-op flow does not read the game over menu: the guest waits muted and continues (Enter) once the host is in game again, assumed to be the default choice (unverified).
- **Save sharing:** the host's typewriter save goes to the Steam cloud through the remote-storage proxy; a successful write sends SAVE_CHANGED to the launcher, which re-sends data0.bin (2.3 MB) to the guests, so a continue after a game over loads the same state everywhere.
- **Submenu open:** sSubMenu::open 0x5d9030 (thiscall, no args) resets the menu and sets state +0x2c = 0; it runs from 0x60bef0 and shows the focused character's inventory. States then step 1..6 while open, 7/0xb/0xc on the way out, 0x0d closed.
- **door_sync:** hooks sDoorLoad::start 0x552b50 (thiscall (room, entry, a3, a4, flag), ret 0x14; stores +0x20/+0x24/+0x34/+0x38, resets the phase +0x44 and switches sRoomControl to the door phase; callers are the door script request 0x552ae0 and two other script paths). The owner of the focused character runs it and sends DOOR_CHANGE 0x010B {room, entry, a3, a4, flag, u8 character}; the other machine suppresses its own starts and runs the received one on the game thread once no door is active, so it plays the door and loads the room normally. Calling changeRoom 0x610c60 directly skips the door animation and leaves the room half-loaded (room reads 0xffff until a camera cut). F8: doors sent/run/blocked.
- **Only the focused character can act on doors:** door (and other interaction) scripts use the condition 0x564070 (cdecl bool(void*, ctx*)): controlled player +0x16e4 (trigger zone; also kept for the partner, -1 outside any zone) == ctx +8, getPad(0) action pressed (pad vtable +0x48), sPlayer 0x4ec1e0(7) == 0. The door script then calls sDoorLoad::request 0x552ae0 (from script opcode 0x579010); sDoorLoad (vtable 0xcd3120, update 0x552300) counts down +0x2c and calls the thunk 0x552720 -> changeRoom. door_sync runs the check with sPlayer +0x2c temporarily set to the local partner when the peer owns the focused character; when it passes, focus moves to the local character first, and DOOR_CHANGE carries that character id so the peer focuses it too.
- **In current room:** player +0xc attribute flags, bit 0x4000 set while the character is in the loaded room (clear for a partner left elsewhere).
- **Current stage/room:** sGameInfo (global 0xdcbe9c) +0x2a80 stage, +0x2a84 room; the record at +0x2a88 keeps the previous room in its first dword. uScrDisp (recreated per room) also has mStageNo +0x30, mRoomNo +0x34, mReqRoom +0x44 (from MT property registration at 0x63a950).
- **Door transition:** sDoorLoad (global 0xdcbeb8) +0x44 (i32): 0 → 1 → 2 → 4 during the transition, 5 idle afterwards; after a fresh save load the idle value is 0xFFFFFFFF (-1), so a door is running only while the phase is in 0..4 (`door_phase.h`). F8 panel lines: door phase (raw), room (hex).
- **Inventory / pause menu:** sSubMenu (global 0xdcebd0) +0x2c: 0x0d closed; other values while a submenu or the pause screen runs.
- sGamePause (0xdcbea8) +0x24 is only a focus-loss marker; setting it does not pause the game.
- **Adapter door/menu behaviour:** `door_travel` latches the door start (game tick and net thread, level-triggered) with whether the partner had the in-room flag. The partner is not moved by the adapter: writing partner +0xff4 (room object) and position makes it visible but leaves the game's room membership half-updated (E command refused, crash when the partner later walks through a door). Instead party_mode mirrors TEAM/LEAVE_BEHIND into the game's own follow flag, sPlayer +0x40 (u8, 1 = partner follows; the vanilla E toggles it), so the vanilla door logic carries a following partner. No partner AI is given at door start; partner_think skips applying while the door runs and for 30 frames after (polled every tick from `game_state::doorActive`). Arrival sends ROOM_STATE {u16 room, u8 partnerInRoom, u8 pad} and forces one position snap. PLAYER_STATE carries `room` in the former reserved bytes; corrections only apply when the rooms match. Remote-owned characters are corrected continuously after their own move: drift under 3 is ignored, up to 60 moves 0.25 of the way (position and rotation) toward the owner's newest state extrapolated by velocity (capped 100 ms), beyond 60 snaps. `menu_mirror` sends MENU_STATE {u8 open}.
- **Save:** the full data0.bin image is assembled in memory and written by 0x6133d0 → 0x612ad0 → 0x8b3280 → 0x8b3940 → ISteamRemoteStorage::FileWrite("data0.bin", buffer, 0x23a8f0). The step that serializes the live game into a slot (typewriter) is upstream and not found yet.
- Other statics: sRoomControl 0xdcbeb4, sLoading 0xdcf688. MT property names ("mRoomNo", "mPause"…) point at registration code that gives exact offsets.
- **D3D9 device:** hook d3d9!Direct3DCreate9 inline before the decryption wait; the game creates its device within about 1 s of start. (0xdc0790 is not a reliable device pointer.)

## Unit update dispatcher and world freeze (2026-09-29, static disassembly)
- `sUnit::updateAll` **0x727b50**: thiscall, no args, plain `ret` (vtable 0xd1bfd8 slot 6, also referenced by vtable 0xcf3bf8). Once per frame, called from 0x67ce00 (`call [eax+0x18]`) via 0x72373c. Wrapped in a scope object (0xa3b4e0/0xa3b510), loops groups `i < [0xe2d434]+0x620` calling slot 9.
- Slot 9 **0x7279e0**: thiscall, 1 stack arg (group index), `ret 4`. This is the function containing return address 0x727b0e. Per unit in the group's list (+0x2c, next at +0x14): state 1 runs unit slot 5 (init) and becomes 2; state 2 with flag 0x400 calls unit slot 8 (+0x20), the move chain (player slot 8 0x526b30 leads to `uPlayerBase::move` 0x513190 through slot 41 0x51b680). Units flagged in the group's +0x28 bit 0 are queued on a job list at [0xe2d904]+0xac instead. Slot 10 (0x727bb0, run per frame by slot 11 0x727ce0) is a second phase: after init it calls unit slots 8 and 10 once, then unit slot 9 (+0x24) each frame.
- Neither function touches a pad, input or a render call: they only walk unit lists. The engine itself early-outs both when `[0xe2d904]+0x60 == 0 && byte [0xe2d904]+0x64 != 0` (its own pause), so skipping the whole call is a state the engine already supports.
- Adapter freeze: `menu_mirror` hooks 0x727b50 (once per frame, no args) and returns without calling the original while a peer's menu is open and ours is closed. Rendering, input polling and the net thread keep running. Side effects: `game_tick` callbacks (run from the controlled player's move) do not fire while frozen, so the freeze state is evaluated in the detour itself and MENU_STATE is sent from the net thread. The second phase (unit slot 9, e.g. animation/motion) is not hooked and keeps running, so frozen characters may still animate.
- Untested in game: whether the vanilla pause menu itself stops calling 0x727b50; door state values seen only at the ends of a transition when the callback stops firing.

## Items (2026-09-29)
- sItem* 0xdcbf44 holds inventories as fixed per-character blocks (unchanged by the V switch): **Rebecca at +0x24, Billy at +0x64**, 0x40 bytes each = 6 slots of {u32 itemId, u32 count} plus 0x10 of extras (third extra dword = the equipped slot index). 0xb4 marks the second half of a 2-slot item. Seen ids: 0x68 Hunting Gun, 4 Handgun, 0x20 Handgun Bullets, 2 Knife, 0x2d herb.
- sItem slot writers: set 0x4dae04/0x4dae8b, remove 0x4db2b9, add on pickup 0x4dc269. The drop (Leave) runs through the player's update: 0x513570 → 0x500db2 → 0x50e1c4 → 0x5d763e → 0x4dc750.
- sItemPut* 0xdce0a8 = the dropped floor items. Layout (static, from the ctor 0x4de150, dtor 0x4de1f0, DTI 0xdce9bc, vtable 0xcc7bfc, getDTI = slot 4 0x4df910): the object holds **28 records of 0x24 bytes at +0x20** (ctor loops 0x1c+1 times calling the record ctor 0x4de0c0; initial record = all zero except the dword at +0x14 = -1). A cleared record seen at runtime: {u32 room?, ..., u32 itemId, u32 count, u16/u16 position-ish, i16 -1, i16 -1, u8}. Field meaning is NOT confirmed statically, and there is no used flag found: the adapter treats the 1008-byte array as plain data and compares it whole. The names mUseItemCount/mUseItemHead/mEmptyItemCount/mEmptyItemHead belong to a different class (property list at 0x55cb40, xref of "mpStageEffectManager"), not sItemPut; sItemPut's own slot 3 (0x608180) is generic. Level-placed items live elsewhere (0x4dfa00 reads a stage item table, keyed by 0x71/0x73 kinds; pickup flags not found yet).
- Item sync (adapter): INVENTORY 0x0106 `{u8 characterId, u8 block[0x40]}` reliable, sent by the owner of a character when its sItem block changed and stayed unchanged for 10 frames, and every 5 s; the receiver overwrites the block only if it treats that character as remote-owned. Floor items are synced by event, see below.

- **sItemPut record layout (runtime-checked 2026-09-29):** 28 records of 0x24 bytes at object +0x20: {u32 key, u32 0, u32 itemId, u32 count, **u32 pointer to the spawned uItem object**, u32 0, u32 0xff, u32 0, u32 0}; an empty record has -1 at +0x14. Because of the live pointer, whole-record overwrites are unsafe. Whole-record overwrites are unsafe, so floor sync replays the game's own put/remove instead.

- **Floor put/remove (static analysis 2026-09-29, untested in game):** `sItemPut::put` 0x4de500, thiscall, ret 0xC, `this` = sItemPut* (0xdce0a8; the caller gets it as `0x404fe0(0x480460(&tmp))`, a weak-pointer accessor chain). Args: (1) `ItemDesc*` {u32 itemId, u32 count, u32 0}; (2) **position** vec3, copied to the new uItem at +0x40; (3) **Euler rotation** vec3, passed (y minus a constant) to 0x719f20, which builds the unit's rotation. The Leave caller (0x5e4b84 in 0x5e1d10) builds arg 3 with 0x67fcc0 = matrix to Euler angles (`this` = a 4x4 built from the player's facing at 0x5e4a63, output pointer returned), so it depends only on the dropper's facing; the adapter reproduces it by forwarding the rotation the local put received. put also reads `sPlayer->controlled + 0xff4` (must be non-null) and returns the uItem. `sItemPut::remove` 0x4de730, `ret 4`, one arg (the uItem*); it loads `this` from [0xdcbf40] itself, so ecx is ignored. Adapter (`floor_items_sync`): both are MinHooked. A local call (not while applying a network event) runs the original and then sends FLOOR_PUT 0x0107 `{u16 room, u16 0, u32 itemId, u32 count, f32 pos[3], f32 rot[3]}` or FLOOR_TAKE 0x0108 `{u16 room, u16 0, u32 itemId, f32 pos[3]}` (reliable; the take reads itemId and position from the uItem before the original frees it). Calls made inside a remote-owned character's move scope are suppressed and not broadcast. The receiver (game thread) applies an event when `room` equals our current room and the room is ready (no door running, 30 frames after door arrival, item table and controlled character present); otherwise it goes to a per-room pending queue (`floor_pending`, cap 32 per room, oldest dropped), where a TAKE cancels the nearest matching pending PUT (same itemId within 50 units) instead of being stored. When a room becomes ready its pending events apply in arrival order through the same apply code (reentrancy flag, no re-broadcast). RE0 keeps no plain in-memory table of other rooms' floor items (only the current room's sItemPut; other rooms are presumably in the save image), hence the adapter-side queue. Not covered: a late joiner sees nothing already on the floor, and the queue is lost on restart. F8 panel: floor pending (gauge), pend appl/drop. TAKE finds the local record with the same itemId whose uItem (+0x40) is within 50 units and removes it; no match counts as a take miss. Risks: put may also run when a room loads persisted items (would duplicate for a peer already there); the suppressed remote-move case assumes Leave/pickup run inside the character's move.

- **Pickup action (corrected 2026-09-29):** step 0x500d00 (thiscall, state object, 1 arg player, ret 4; state +0x10 phase 0 start / 1 take / 2 done, +0x18 = the player). The take reads `[player + 0x67a0] + 4` (0x4ded40 is just that accessor), and player+0x67a0 is the interaction target, cleared when the item is removed, with no null check (crash at 0x500da3). The adapter's pickup_guard ends the action (phase 2) when the target is null.

- **Room membership (confirmed in-game 2026-09-29):** player +0xff4 = pointer to the room object the character belongs to. Each frame the player update (0x529990..0x529a1f) sets "hidden reason" bits in +0xfc8 through 0x6534f0(bit, set); reason bit 2 = 0x61b0b0([0xdcbf40], room obj, 1), i.e. "room not loaded". +0xc bit 0x4000 (active/in room) is on only when +0xfc8 & ~1 == 0. **Setting a partner's +0xff4 to the focused character's value and writing its position (+0x40) brings it into the current room** (tested: reasons 0x4 -> 0, the partner appears).

## Keyboard (config.ini)
W/S/A/D move, Space run/attack, Shift aim, F action, **V switch character**, E partner follow toggle, arrows move the partner, Q map, C status. **Space cancels menus**; Esc opens pause (Quit Game is on that menu).

## Co-op design direction
Each client controls its own character. On each machine, the remote player is the partner. The partner is driven by network state; replacing its think vs mirroring its state is decided after in-process tracing.

## Party command path (revised 2026-09-29)
E/V are polled by `command_input::onNetTick` on the net thread (~5 ms), not from a game_tick callback and not from the render path: the net loop keeps running through menus, doors and the world freeze, so the raw-key edge detector never stalls (a hook-driven detector missed edges whenever move() stopped). A press logs `command: <name> pressed (keyboard|controller)`; it becomes a request in gameplay with a peer connected. Host and guest presses share one request path (`party_mode::queueToggle`; a guest's PARTY_REQUEST calls the same function); the host decides on the game thread and logs applied or ignored with the reason. Panel: last command and last decision with age. `key_config` reads the first `KC_change`/`KC_trace` line in any section whose value is a known `KB_` name.

## Separate rooms study (2026-09-30, unmodified game, solo)
Goal: both players in different rooms at once (each machine loads its own player's room). Findings so far:
- Leaving the partner behind (E = stay, controlled character takes a door) clears the partner's in-room bit
  (+0xc 0x4000); the game keeps simulating only the loaded room.
- Each character has an `sCollision::SbcInfo` at +0x1870 (vtable 0xcc3fb4): +0x1880 stage, +0x1884 room of the
  collision set it uses. The left-behind partner keeps its old room there (2, 3 in the test).
- **SbcInfo is not the partner's room record.** Rewriting the partner's SbcInfo room and position, then reloading
  rooms, changed nothing: on return the game placed the partner back in its real room at a position of its own
  (241, 600, 2852) and set the in-room bit. A separate partner room/position record exists.
- Current-room record: sGameInfo +0x2a7c {entry, stage, room, previous room}; +0x2a90..+0x2a9c gets a copy once
  the characters split (0xffff while together). Candidate for the partner's room: sGameInfo +0x1e5c (3 in both
  snapshots, the room the partner stayed in); needs a third sample with the partner in a different room.
- Controls in this setup are camera-relative (D moves right on screen), not tank controls.

What separate rooms needs, in order:
1. The partner room/position record (write it when the remote player changes rooms, so a reunion places them
   correctly through the game's own logic).
2. Camera parity off while apart: each machine focuses its own player's character.
3. door_sync only between players in the same room (already the TEAM rule) and no door forcing while apart.
4. Enemy authority per room: whoever is in a room simulates its enemies; host authority only when together.

**Scene records (static analysis of the door carry 0x61e2c0, confirmed in game 2026-09-30).** sSceneInfo (0xdcbf40)
keeps up to 4 room records (pointers at +0x2dc70); +0x20 is the loaded one. A character belongs to the record at its
+0xff4; a room a character was left in stays as a dormant record (that is the "hidden" partner room: record +8 = scene
id, the same id doors pass, e.g. 0x59, 0x61, 0x24; +0x9aa4 = entry spots, 0x18 bytes per (entry * 3 + mode)). The carry
moves a character with: [0xdcc010]->0x411570(-1, player +0xff0) (unit registry, detach); 0x61e0f0(scene, flags)
on sSceneInfo (find the room's record, or load it dormant; flags = [0xdd1d44] | 4); 0x61ed50(player, entry, mode) on
the record (entry spot, mode 0 = through the door, 2 = following partner); 0x619e30(record, player) on sSceneInfo (leave
and enter callbacks, +0xff4); 0x411570(scene, handle) again; 0x61dde0(record) releases an empty dormant record.
`scene::move` runs exactly that for one character. Tested with the fake session: Billy sent from the loaded 0x59 to
0x24 vanished with no screen change; sent back he stood at the door's spot (241, 600, 2852, where the game itself puts
him); moved away (0x59 released) and back (0x59 loaded fresh, same slot reused), then Rebecca walked into 0x59 through
its door and found him there. A rejoining guest took Billy through his door into 0x61 and Rebecca was moved into
dormant 0x24; the fake host's Rebecca then walked into 0x61 and appeared at the door. The in-room flag (+0xc 0x4000)
of a character moved into a dormant record can stay set (it only updates while the character's room runs), so "in the
loaded room" also compares +0xff4 with the loaded record.

So split rooms needs no replay: a peer's door moves the peer's character in place (split_rooms.cpp, always on), the
save and later doors see the engine's own state. LEAVE_BEHIND is independent play (nobody follows; the own camera on each machine is
unconditional since 2026-10-06). Enemies: the machine that was in a room first keeps simulating it when the other walks in (ROOM_STATE carries
the claim; host on a tie). **A dormant record never spawns the room (2026-10-06, first two-PC session).** `0x61e0f0` returns an existing record of the scene at once (and with flag 2 makes a second one), so a record `scene::move` made dormant for the peer's door is reused by a later local door into that room: no room load runs, the room has no enemies or floor items (log: `enemy_state: slot 0 has no local enemy`). Cause inferred from the log and the disassembly, not yet seen live. `split_rooms::beforeLocalDoor` therefore moves a peer character that sits alone in the target's dormant record into the loaded room (which frees the record), the door loads the room fresh like a never-visited one, and `onArrival` moves the character back to its door entry. Enemy state then applies slot by slot as before. Retest: guest enters a room first while split, host walks in, enemies and items exist on the host.
Cutscenes that move the peer's character hand the result to its owner (event_place).

**The game's own switch (V)** is a multi-step action in the player think (0x4fec64..: states 3/4/5): in the same room it
swaps directly (no room phase), apart it requests Change from 0x4fed48 / 0x50395e. Refusing requestPhase(Change) misses
the first path, so the switch is cut at its input: the DirectInput keyboard never reports the KC_change key during co-op
(virtual_keys), which also keeps it out of the pad frames the peer replays. A gamepad's switch button is undone by
camera_parity's focus keeping (always, with a peer).

**Zap right after a load asserts (2026-10-01).** Requesting the Change phase 0.1 s after a save reached Main (the
own character dormant in another room) crashed in the engine's room-record assert (strings 0xcb57ac/0xcb57d0, via

**Apart includes the own character.** A save can split the two (slot 2: Rebecca in scene 0x04, Billy dormant in 0x0a).
A guest loading it sees the host's room while its own Billy is elsewhere, so "apart" is also true when this player's own
character is outside the loaded room: the camera goes to it (zap, after the settle) and its room loads. Verified with

**Peer doors wait for plain gameplay.** door_sync ran a peer door during a local status screen: the door's character
took the camera and the door itself never started (lost). Doors, placements and the party commands now all wait for
`game_state::playing` (Main, no door, no menu). In the status screen the command keys are the game's again.

**Boot-time save:** on the boot notice screen the game issues its own save request for slot 0 (no room phase). Redirecting

**Motion forcing and update skipping removed (2026-10-06, Build 139 crash and frozen enemies).** Host crash 0xc0000005 at 0x4fd370: the player think reads the low byte of the motion number (+0x4a4, via 0x50e0a0) as the key of a table lookup (0x4f9700, tables 0xccb788 / 0xccb7e0) and dereferences the result without a null check. `state_correction::followMotion` wrote the peer's motion number into the remote-owned character with the setter 0x73ef50 while its own state machine was in another state, so the key was not in the table and the lookup returned null. The motion number belongs to the character's own state machine: never write it from outside. The enemy side had the same risk and its sync was also unproven (the +0x4e0 field, read as the frame, was never seen advancing: it is `mInterFrame`, the blend length; the frame is +0x4ec); the guest's enemies were frozen because slot 41 is the whole per-class update (AI dispatch, animation and physics together), not just the AI. Still open: suppressing only the AI decisions of a puppet; each class has its own slot-41 function with its own dispatch (`table[state]` at [enemy+0x67a4] for the 0x420f70 family), so it needs a per-class hook on the dispatch, or restoring the AI-chosen state after the update. Enemy animation parity is open too. Reading the motion block (tools/re0/motion_probe.py) is safe; the layout notes above stay valid.

**Enemy AI dispatch, static findings (2026-10-06).** Every enemy class overrides vtable slot 41 (the per-frame update); 12 of the 18 distinct update functions end in a dispatch `table[state]` through a per-class table of function pointers, indexed by the shared base field **+0x67a4 (AI state index)**: 0x420f70 family (15 vtables) table 0xd7ab60 (5 states), others 0xd7bfcc, 0xd7cef0, 0xd7d588, 0xd7dad0, 0xd7ea08, 0xd7fbf8 / 0xd7fb60, 0xd80248, 0xd80b30, 0xd817a8, 0xd82408, 0xd82bd0, 0xd843fc, 0xd85338, 0xd8607c / 0xd86090; 6 classes (0x443610, 0x46cff0, 0x48af40, 0x4b24f0, 0x9e2ac0 stub, 0x4d7a90 with several) dispatch differently. In the 0x420f70 family the table entries are thunks `mov eax,[ecx]; jmp [eax+K]` into virtual slots 65..69 of the same object: the state handlers are virtual methods, and they mostly watch conditions (scene id at [record+8] via 0x526490 = [enemy+0xff4], HP via 0x522df0, 0x4cb950 flag tests) and request the next state through virtual slot 63 (+0xfc, `setState`-like, 4 arguments in the overriding classes: (1, newState, 0, 0)). The state writers (+0x67a4) are spread over 55 sites in the class code. So the AI is a state machine whose transitions are virtual calls: a puppet can be made to hold the owner's state by (a) sending +0x67a4 and skipping the transition-checking handlers, plus (b) running the class's own transition (slot 63) when the owner's state changes so the animation starts the way the game starts it. Neither is safe to write blind (an unmatched motion crashed the host today); it needs a live sample of state, motion and frame on a moving enemy: `tools/re0/enemy_state_probe.py` (read-only, prints every change of +0x67a4, motion number and frame). No enemies were loaded during my 10-minute probe.

**Weapon swap found and synced (2026-10-06, second watch on player +0x6838).** The weak pointer at player +0x6838 (the held weapon unit) is set by `0x529320` from `0x509c20` (attach the weapon unit), called by `0x50d870` = `player->setWeaponType(type)` (thiscall, ret 4: stores the type in +0x6950, creates the weapon unit through the factory 0x51fa20(…, 0x74, record, type), attaches it, re-applies the aim, and for a knife calls 0x50d6e0). The menu-close routine at 0x5d7740..0x5d77e3 runs, for the controlled player and the partner: `block = 0x50dc70(player); type = 0x4db2f0(block, block[+0x3c]); 0x50d870(player, type); if slot != -1 { 0x50d670(player); 0x516630(player) }`. +0x6950 is therefore the weapon type (3 handgun, 5 shotgun in the trace), +0x0fe8 its copy (0x526500). The adapter ran none of it for a remote-owned character, only copying the inventory block, so the partner kept the old weapon. `equip_refresh` replays that sequence when a received block changes the equipped slot of a remote-owned character (both directions, as each machine treats the peer's character as remote), after the resource step below (running the sequence alone T-posed the character).

**Enemy probe reading (host, 60 s, tools/re0/out/enemy_probe.txt).** AI state (+0x67a4) stayed 1 for the 0xcc5508 and 0xcc4f28 families while the motion number (+0x4a4) changed constantly (0x05f, 0x005, 0x02f, 0x037, 0x016, 0x01a, 0x00c): the motion number tracks the animation, not the AI state, so holding the state index would not match it. At each motion change the value at +0x4e0 (`mInterFrame`, the blend length; the frame is +0x4ec: corrected 2026-10-19) was a small number (0, 2, 4, 9, 16) and the total (+0x4f4) the motion length, which was read as a current-frame field; the probe only prints on a change, so it never shows the frame advancing, and the later idle samples (enemies not in motion, frame 0 constant) do not either. **Enemy animation match (2026-10-06).** Superseded 2026-10-07 ("One decision maker per enemy" below); kept for the findings. Vtable slot 63 (+0xfc) of the enemy classes is `setAction(state, id, a, b)`: it stores the four ints at +0x67a4 / +0x67a8 / +0x67ac / +0x67b0, and the class's state handlers (slots 65..) start the motion for that record. Live probe (host, three enemies): records such as (1,2,1,0) with motion 0x004, (1,3,1,0) with 0x00c, (1,5,2,1) with 0x037, (1,8,0,1) with 0x016, (1,8,1,1) with 0x01a; a lying enemy shows (3,3,0,0) with 0x01b. The record is therefore what the AI chooses and the motion follows it; the state word alone (1) does not. The value at +0x4e0 stayed 0.00 / 16.00 on enemies that were moving across 1 s, so it is not a running frame (it is `mInterFrame`, the blend length; the running frame is +0x4ec: corrected 2026-10-19), which this design did not need. Implementation: the owner sends the record; a puppet whose record differs from it for 200 ms while the owner's has been stable for 120 ms is told the owner's record through its own setAction (the call its AI makes, never a raw write of +0x4a4), at most once per 400 ms. Only the five slot-63 implementations with four arguments (0x4cc670, 0x44d820, 0x4650f0, 0x480c20, 0x4bbc70) are called; 0x48ac80 (ret 8) and 0x4b17f0 (ret 4) are left alone, a wrong argument count would unbalance the stack. Not verified live: watch the F8 "enemy action requests" counter and the guest enemies' animation.

**Door entry spots (2026-10-06).** A record keeps three spots per entry (+0x9aa4 + (entry * 3 + mode) * 0x18, {x, y, z, facing}); read live in scene 0x37: mode 0 the door spot, mode 1 50 to 70 units beside it, mode 2 50 units behind it, except that at some entries mode 2 equals mode 0 (entry 1 of 0x37). The engine's own carry puts a following partner on mode 2. `scene::move` always used mode 0, so a peer's character placed into a room where the other character already stood (the peer arrived second through the same door, or the equip/room-free park of `split_rooms::beforeLocalDoor` returned it) landed on the same spot and the collision threw one of them. `spot_rule::modeFor` now picks mode 2 when the other character is already in the target record, mode 1 when mode 2 is the door spot, else mode 0. Both machines place only the REMOTE character this way; the local one is placed by its own game and state_correction then pulls the remote copy to its owner's real position, so one side (the owner) decides where a character stands. The game's TEAM carry through a door was already on mode 2. No collision query was added: the spots are the game's own, authored for two characters.

**Owner AI replication on the non-owner (2026-10-06).** Superseded 2026-10-07 ("One decision maker per enemy" below); kept for the findings. (1) The setAction slot (63) is patched on every enemy vtable with a generated thunk (`slot_thunk`, N = 4, 2 or 1 stack arguments by implementation: 0x4cc670 x32 classes, 0x44d820, 0x4650f0, 0x480c20, 0x4bbc70 take four; 0x48ac80 two, 0x4b17f0 one). On a puppet that is alive and has an owner record the enemy's own call is dropped; everything else (the owner machine, an enemy with no record yet, a dead one) calls the original. Our own application bypasses the thunk by calling the original directly, so no flag or thread guard is needed. Handlers that write the record directly are undone by the update wrapper (next paragraph); the 100 ms cooldown stops a flip-flop from re-applying every frame. **Direct state writes and the target (2026-10-06, static, image.bin; `tools/re0/field_refs.py`, `slot_funcs.py`).** (1) Writers of the record word +0x67a4: 83 `mov [reg+0x67a4], imm/reg` sites in the class code (state 1 and 2 mostly; the rest of the 160 references compare), none of them through setAction, so the setAction thunk cannot see them. Slot 41 (the update, plain thiscall, no arguments; the sUnit callers push nothing) runs them all, so `enemy_action::onUpdate` wraps it: on a living puppet the four record words are saved before the update and written back after it. Our own setAction application happens outside the update (game tick), so it is untouched. Why a restore and not only a skipped think call: in the 0x420f70 family (15 vtables) the update dispatches `table[state]` (0xd7ab60) to virtual slots 65..69: state 0 (slot 65, 0x41e260) sets the enemy up, state 1 (66, 0x41ea80) is the action executor (per-action begin/update tables indexed by +0x67a8, then 0x4cc6a0), state 2 (67, 0x41db20) is the **think**: a chain of transition checks (0x422fe0, 0x423680, 0x423590, 0x423e90, 0x424340, ...) that end in setAction, then a per-action table call; it only sets flag bits (+0x6844, +0x684c) and moves nothing. That one function is shared by all 15 vtables and is hooked by MinHook (`enemy_action` `onThink`): on a living puppet it does not run. The executor and the per-action functions mix animation and movement with their own `state = 2` writes (action finished), so they cannot be skipped (a skipped whole update froze guest enemies, Build 139); the restore undoes those writes. The other 12 update implementations dispatch through their own tables with decisions and execution interleaved the same way; each would need its own analysis, so they get only the restore. (2) Target: the 15 vtables whose update is 0x420f70 call 0x421b20 from it (only caller, 0x421019). It takes sPlayer +0x2c (controlled, getter 0x4ec780) and +0x3c (partner, getter 0x96cd30), stores the distances to them in the enemy at +0x67cc / +0x67d0 (3.4e38 when that player is in another scene record), and picks the target with `comiss`: the partner only when strictly nearer; flags 6 and 2 (0x4cb4d0) force the controlled one. Because each machine's controlled player is its own character, a tie or a flag picks Billy on one screen and Rebecca on the other. The owner sends the character id (ENEMY_STATE entry byte 1, 0xFF none); `enemy_target` hooks 0x421b20 and, on a puppet, overwrites the three fields with the local object of that character. Other writers of +0x6b80: 0x43a016..0x43a182 (the own-class selector 0x439e90 of vtable 0xcbf0d0, called from its update at 0x43933d, plain thiscall; it writes the target object and +0x6b84 as the flat x/z distance (0x521bd0) and leaves +0x6b88 as a range, so its hook rewrites those two; its later range logic still uses the locally chosen target), 0x4c02e1 clears it. **Other update implementations, local flags, kill persistence (2026-10-06, static).** (1) The 83 direct `mov [reg+0x67a4], x` sites are all in the other classes' code (0x44d9f7 ... 0x4e80a0): the 15 base-family vtables contain none (only compares), so for them the setAction thunk plus the skipped think already leave the owner's record as the only writer; the update restore is only a fallback for the rest. `tools/re0/think_scan.py` profiles every state-dispatch table entry of the 15 other update tables (setAction calls reached within two direct calls, direct state writes, position writes). **Enemy sync v2 (2026-10-07; review and evidence in docs/re/RE0_ENEMY_SYNC_REVIEW.md).** Build 158 had two or more writers on every piece of an enemy's state (pose blend vs its own movement, four writers of the action record, snapshot HP vs replayed damage), which matched the live reports (jitter, stuck animations, one-screen hits). **Hits replay the owner's outcome (2026-10-07, static).** The damage function is not deterministic: its first call, slot 76 (0x4cbdb0, shared by 37 classes), rolls the game's one random generator (xorshift128 0x684d90, state four words at 0xe2ccb0) through randRange 0x6600c0 (0..99) against a per-weapon chance from sEnemy 0x417270 and sets the critical flag +0x6a0c bit 0x1000000; class 0x438b00 rolls it via 0x660080 (random float). Now the owner records the enemy's HP and the random state, runs the damage function, and sends both with the hit point relative to the enemy (HitPayload 52 bytes). The receiver sets that HP, writes the random state, runs the same function around its own enemy and writes its own random state back. Whoever receives HIT_REQUEST applies it as owner and whoever receives HIT_APPLIED replays it (Build 158 dropped a request on a machine that did not believe it owned the room, and an applied hit on one that did, so every hit was lost on one side while the two disagreed at a room entry). **Enemy creation seeded (2026-10-07, static).** Every enemy is built by sEnemy's create 0x410bb0 (thiscall (a, record index, b), ret 0xc; called from the room setup 0x4109d0 <- 0x61b2f0 and from script opcodes through 0x4109f0), from the spawn record this + 0x30 + index * 0x5c (index < 0x4e8; +0x4 kind, +0x10 spawn id, the kill flag is 0x612 + it), and ends in the class's spawn init, vtable slot 36 (`call [edx+0x90]` at 0x410e67; 18 implementations, 0x420ce0 for the base family). 0x420ce0 copies the spawn id to +0x67c4 and the home position, then: record +0x40 == 0xff (spawned before) takes HP from record +0x3c and the variant from record +0x50; otherwise HP comes from a table (0x4ca860) and the variant +0x6ab0 = rand % 3 (generator 0x684d90 on 0xe2ccb0), and record +0x40 is set to 0xff. +0x6ab0 is read during play (0x419450, 0x41a1a2, 0x41e86f, the update 0x420efb, 0x421b00 next to the target selector), so the two machines' first spawn of a zombie could behave differently from the start. `enemy_spawn` hooks the create: it runs with the random state set from the scene and the record's index, kind and spawn id (`spawn_seed.h`) and the game's own state is put back after it, so every class's spawn rolls match on both machines and nothing else's randomness changes. Always on in co-op (a room created before the partner joined matches too). The variant of a first spawn is then a fixed function of the record, not random per playthrough. Assumed: the create runs on the game thread (its callers are the room setup and the script opcodes). Every create also clears the new enemy's pool slot of what its previous enemy left (a waiting owner decision, the follow state): script spawns replayed by event sync can reuse a freed slot in the same room.

**Owner reactions (2026-10-07).** HIT_APPLIED also carries whether the owner's damage function changed the enemy's record (state or action id) and the record right after it (80 bytes). **QoL pass (2026-10-06, nothing run live: no second PC; pure rules unit tested, wire shapes checked with `fake_session.py`).**

- *Host leaves.* `state_sync` sees the host's slot drop out of the peer list while the link is up: toast "Host left: not saved", the partner status line says "Host left / not saved" until a player joins again, saves stay refused. The guest keeps playing the session copy (the cleaner choice: no forced return to the title, nothing to hook).
- *Partner status line.* Top-right, always on with a peer: `name / Fine|Caution|Danger / same room|room 0x24 / in menu`. Condition is hp against the highest hp the partner reported (floor 150): above 50 percent Fine, above 25 Caution, else Danger; the game's own ECG thresholds were not read. - *Resync.* F9 in gameplay or `coop\resync_now.txt` (either machine) or a room desync that lasts 10 s (3 tries, 10 s apart): a guest re-requests the join snapshot and applies it like the first one (flags, both inventories, door travel, the host's character placed); a host sends RESYNC_REQUEST 0x0114 and the guest does the same. ## Outfits (static, 2026-10-13; all addresses read in the decrypted image, not yet run live)

An outfit is one model byte `emXX`. **sPlayerCostume** 0xdcc00c: +0x54 / +0x60 current outfit entry of Rebecca / Billy (12 bytes, first byte = model); `0x546b70(kind)` current model, `0x546940(kind, model)` entry of the family list (the current entry when absent), `0x547130(kind, model)` setCostume (ret 8, family list only; also writes sGameInfo +0x48 Rebecca / +0x49 Billy). **Offered set.** Rebecca 02 S.T.A.R.S. 2002, 7d Western, 81 Leather, 91 Team Wesker; Billy 05 Prisoner, 95 Jacket, a5 Wesker (Billy's outfit, the engine's Wesker Mode path with the cutscene motion rewrite 0x549e60). The owner reports the current outfit of its character as APPEARANCE 0x0116 (`{character, model, 2 reserved}`, reliable, on a change and every 2 s); the peer puts it on that character (`appearance.cpp`). A suitcase change of the partner's character is answered as done and dropped.

## Pose puppet (partner_mode=state; static study 2026-10-19, phase 1 built and unit tested, not run live)

A second way to show the remote-owned character: instead of replaying the owner's pad through the game's think (`partner_mode=input`, the shipped default), the owner's sampled pose and motion requests are replayed on a puppet. adapter.ini `partner_mode=input|state` (any other value is logged and ignored). With `input` none of the code below is installed: no hook, no move scope, no post-move sample, `puppet::active` is always false. Study with evidence tags and the phase plan: `docs/re/RE0_POSE_REPLICATION.md` (V = read in the decrypted image, N = from these notes, I = inferred).

- **The engine's own puppet mode.** Room scripts pause a character's brain with `PlayerPause` (0x56c620): sGameInfo (0xdcbe9c) +0x50 bit 1. `uPlayerBase::move` 0x513190 tests it at 0x5131d4 and then only animates (slot 31), cancels the root motion (`pos -= +0xed0` unless +0x6a70), rebuilds the matrices (0x71ace0) and collision shapes (slot 19, 25) and returns: no think, no locomotion. The bit is global, so `puppet` sets it only inside the remote character's own move (a second move scope in `game_tick`, entered after `input_redirect`'s, exited before) and keeps it set when a script had it set.
- **One funnel for motion requests.** `cAnimControl::set` 0x4144d0 (member at player +0xff8; thiscall (layer < 8, motionNo, flags, f32 interp, f32 start), ret 0x14, no return value; four callers, the uCharaBase wrappers). Read in the image: flags 4 -> attr 0x40000, 8 -> 0x30000, 1 -> 0x10, 2 -> a no-loop byte, and the raw flags are kept at anim control +0x10; bit 0x10 of playMotion's flags (keep root motion, stored at +0x6a70 by `playMotion` 0x509730 only) has no meaning in `set`. So the puppet writes +0x6a70 = 0 itself on every move and also clears 0x10 from layer-0 flags it replays (`puppet_rule::replayFlags`). The owner side hooks `set` (`pose_game`) and sends each call made on its own character; the puppet replays the same call through the original, after `0x73e650` (motion available in the banks of the puppet, thiscall (motionNo) ret 4, returns a pointer or 0) says the motion is loaded; a miss is counted and the request skipped (the engine would clear the layer to the bind pose). A request for motion 0xffff (clear the layer) is replayed without the check.
- **Wire.** POSE_STATE 0x0140 (unreliable, 30 Hz, 56 bytes since phase 3, `pose_wire.h`, fields in "State mode: timeline and POSE v2"). MOTION_EVENT 0x0141 (reliable, 24 bytes): owner clock ms, sequence, layer, motion number, flags, interp, start. Both carry the owner's `monotonicMs` low 32 bits; decode refuses wrong sizes, non-finite numbers and out-of-range fields. The target character is the remote-owned one (`character_owner`), the frame's slot must be `net_pad::peerSlot()`.
- **Receiver.** `stream_clock.h` and `pose_timeline.h` (pure; rules in "State mode: timeline and POSE v2"): the shown state is the owner's 100 ms behind: position lerp, rotation slerp (`position_blend`), frames lerped on the same motion, discrete fields from the older sample; events due are handed out once, in sequence order, older than 1 s dropped. Per puppet move (`puppet.cpp`, before the engine's move): render, skip when a door runs, the room phase is an event, the pose's room is not the loaded one or the character is not in it; else write position, rotation, +0x6a70 = 0 and the think group / state / phase (only when the think is a cPlayerThink, a partner AI keeps other data there; raw writes are safe because the think never runs while the bit is set, the Build 139 crash was a motion write under a running think), replay due events, then `puppet_rule::SeekTracker`: when layer 0 shows another motion, or the same motion more than 6 frames apart (wrapping at the motion's frame max), for 6 moves in a row, the owner's motion is requested again at the owner's frame with interp 0. Then the pause bit is held for the engine's move. `input_redirect` gives a puppet the neutral pad (route Puppet; floor item suppression stays on), `state_correction` leaves its position alone, the HP sync stays.
- **Hits on the puppet.** The damage and grab entry is vtable slot 34 of both players: the same function 0x512570 in both vtables, thiscall with five stack dwords (ret 0x14; the study counted four arguments), returns 0 while the pause bit is set. Enemies update outside the puppet's move, so `puppet` MinHooks 0x512570 (`player_contact` since phase 4) and answers 0 for a puppet (a hook on the function, not a patched vtable: one place, no generated thunk). The owner's own character takes hits as before; `enemy_damage_hook` already drops hits whose shooter is remote-owned.
- **Leaving.** When a character stops being a puppet (peer left, owner in another room, mode off) `puppet` calls the script's `Player_Reset` 0x516440 once (thiscall, plain ret; changeState(0, 0, 0), hand pose, flags) before the think runs again.
- **Echo test (one PC).** `adapters/re0/README.md`. Log lines (`adapter.log`): `puppet: Billy is shown from the owner's pose`; once a second `puppet: Billy motion 0x.... (owner 0x....) frame f (owner f) think g/s/p (owner g/s/p) mode flags before -> during -> after, events in N, misses M, seeks S`; `puppet: Billy has no motion 0x.... loaded` (a miss); `puppet: Billy released`. Expected: the motions and frames agree (the echo returns Rebecca's motion numbers for Billy, whose banks differ, so misses are expected), the mode flags before and after are equal and `during` has 0x2 set, no crash.
- **Not yet known (need a live run).** Whether anything reads the pause bit inside the slot 18 / 19 / 25 / 31 calls of another unit during the puppet's move; how visible a seek is while blending; the enemy side of grabs; weapon fire effects, reload and the frame-driven weapon swap 0x5178b0 (phase 2); status flag mirror and script threads aimed at the puppet (phase 3); doors, rooms apart and join (phase 4). The speed (+0x5c) and character id the study listed for POSE_STATE are not sent: the frame is interpolated between samples and the character is the slot's owned one.

## State mode: plumbing (phase 2 of docs/re/RE0_POSE_REPLICATION.md and the state-replication plan; built and unit tested, not run live)

The switches every later state-mode module uses. With `partner_mode=input` none of it is enabled: `state_mode::on()` is false, `state_mode::enableAll` is never called, nothing is registered with the router and every existing module runs its shipped code. Only `init.cpp` and `state_sync.cpp` changed on that path, and neither changes what an input-mode session does.

- **`state_mode`.** `configure(mode)` (from `enableCoop`, before any module is enabled) records `partner_mode`; `on()` answers it from any thread; `enableAll(NetClient&)` enables the state modules in the slot `init.cpp`'s `enableStateMode` had (last in `enableCoop`): `state_net::bind`, the load serial observer, `pose_capture`, `puppet`, `room_authority`, `flag_sequencer`, `weapon_fx_capture`, `weapon_fx_replay`, `enemy_observer`, `item_ledger`. Later phases append their enable call there. Log: `state_mode: on, N modules enabled` (11 now: load serial observer, pose capture, puppet, room authority, flag sequencer, weapon fx capture, weapon fx replay, enemy observer, item ledger, room move, door follow; each counts when its enable call ran); `adapter: state mode unavailable` when a hook failed (the puppet needs the `cAnimControl::set` hook `pose_capture` installs, so a failed capture stops the list).
- **`state_net`** is the only send path for the state block 0x0140..0x017f (`state_net_rule.h`). `send(type, reliable, payload)` goes to every peer; a state type outside state mode is refused, counted (F8 `state refused`) and logged `state_net: refused type 0x%04x outside state mode`, which must never appear. `pose_capture` sends POSE_STATE and MOTION_EVENT through it (so `pose_capture::enable` no longer takes the client). Types outside the block are not this guard's business.
- **`frame_router`** is the receive side: `add(type, SenderPolicy, handler)` (only types in the state block, once each) and `dispatch(frame, hostSlot)`. Policies (`frame_router_rule.h`): Any; HostOnly (the sender is the session's host); GuestOnly (this machine is the host and the sender is not). A frame the policy refuses is consumed and counted (F8 `router dropped`) with `router: dropped type 0x%04x from slot %d (host only|guest only)`. `state_sync::onFrame` hands every frame it does not know to `dispatch` just before the PLAYER_STATE handling; `puppet::enable` registers 0x0140 and 0x0141 with policy Any (the slot check against the driving peer stays in `puppet::onFrame`). Registration happens before `state_sync::start`, so the table is read-only once the net thread runs.
- **Load serial** (`load_serial.h`, `scene::loadSerial()`): a u16, never 0, that advances whenever the loaded room record or its scene id changes, and for the first record after none was loaded (a load in progress, record 0, is not a change by itself, so a record that is loaded again at the same address still counts once). `scene::observeLoad` feeds it once per game tick (a game tick callback registered by `enableAll`) and logs `scene: load serial N (scene 0x..)`. It exists so a stream can be reset when the scene id alone repeats (left a room and came back to it); POSE_STATE and ROOM_MOVE carry it from phase 3 on.
- **PAD_FRAME.** `input_record::enable` (the PAD_FRAME sender) is registered only in input mode, in the same slot of `enableCoop`; in state mode no pad frame is sent (F8 `pad sent/s` stays 0) and the shipped echo test still shows the puppet because POSE_STATE and MOTION_EVENT carry the owner's body.
- **`tools/re0/player_fields_probe.py`** (read-only, on `probe.py`): both characters' +0x68c4, +0x16ec, +0x1034, think group / state / phase, +0x69cc, +0x4a4, +0x4ec, +0x6950 and +0x695c at `--hz` (default 10) for `--seconds` (default 60), one line per change (the frame alone is not a change). Run it on a solo game to answer the plan's probe F1.
- **Live gate.** `partner_mode=input`: `adapter.log` has no `state_mode:` line, no `router:` line, F8 `state refused` and `router dropped` stay 0, `pad sent/s` is above 0, the shipped echo test behaves as before. `partner_mode=state`: `state_mode: on, 11 modules enabled`, the phase-1 echo gate passes unchanged, `pad sent/s` stays 0, `scene: load serial` shows one new line per door or room change, `state refused` stays 0 and `state_net: refused` never appears. Then run the probe.

## State mode: timeline and POSE v2 (phase 3 of the state-replication plan; built and unit tested, not run live)

One clock per peer, hard resets and the 56-byte pose. With `partner_mode=input` nothing here runs: the only edit on a shared path is one `if (state_mode::on()) pose_capture::onNetTick();` line in `state_sync::tick`.

- **`stream_clock.h`** (pure): the peer's clock mapped to the local one by the smallest transit time (arrival minus sender clock; a later sample moves it 1 ms per 32 samples; a transit more than 5 s off means the peer's clock restarted), `target(now)` = `now - offset - 100`. `puppet` keeps one per peer slot (`puppet::clockFor(slot)` returns a copy; WEAPON_FX, enemy streams and FLOOR_TAKE timing read it so everything one machine shows of the other is one instant). `generation()` changes whenever the clock is cleared or re-anchored; a stream that last saw another generation starts over (reset reason clock). DS2's delay_line / adaptive_delay / clock_offset are a separate policy (STATE_PLAN C8).
- **`timed_queue.h`** (pure template): numbered items handed out once, in sequence order, when the peer's time for them comes; duplicates and handed-out sequences dropped, items more than 1 s behind the shown time dropped and counted, 64 held. The pose timeline's motion events use it (the code moved out of `pose_timeline.h`).
- **`pose_timeline.h`**: render time = `target(now)`. Interpolated: position, rotation, frames on the same motion, aim pitch. Every discrete field (motion numbers, think, weapon, status, +0x1034, hit attributes, aim tier, held) is the older bracketing sample's. No extrapolation: past the newest pose it holds. Hard reset (the buffer is dropped, the newest pose is shown at once and held until its time comes, `Result.reset` says why, the puppet logs it once and seeks at once): `serial` (load serial differs; checked first, so a door logs serial), `room` (room differs, same serial), `gap` (sender or arrival gap over 500 ms between poses; the clock is re-anchored to this pose), `teleport` (jump of 2000 units or more, `kTeleportUnits`, probe E1), `lead` (newest pose more than 250 ms ahead of the shown time: the clock is re-anchored to the newest pose), `depth` (more than 8 poses ahead of the shown time: same), `clock` (the shared clock changed generation). Freshness: any pose, held ones included, keeps the stream fresh; 2000 ms of silence is `stale` (`Result.stale`, nothing shown, the puppet holds and branch A keeps animating the last motion; it never falls back to AI or pad). The plan text says "no non-held pose for 2000 ms" but its own gate (inventory open 5 s with held resends, no stale line) needs held poses to count, so they do.
- **POSE_STATE v2** (56 bytes, `static_assert`): senderMs u32, seq u32, pos f32[3], quat u32 smallest-three, frame0 f32, status u32 (+0x68c4), x1034 u32 (uCharaBase +0x1034), room u16, loadSerial u16, motion0 u16, motion1 u16, frame1 u16 (1/64), hitAttr u16 (+0x16ec & 0x3ff), manualPitch i16 (+0x695c, 1/4096 rad), group / state / phase u8, weapon u8 (+0x6950), aimTier u8 (+0x6954), flags u8 (bit 0 held). Refused: wrong size, non-finite floats, group > 3, weapon > 0x1b, aim tier > 2, hit attributes over 10 bits, unknown flag bits. The capture clamps weapon, aim tier and group into those ranges so an odd engine value cannot make the peer drop every pose. The receiver only carries the new fields (they ride in `Pose` and the timeline); phase 4 writes them to the puppet.
- **MOTION_EVENT** `layer`: low byte = layer (< 8), high byte = anim control (0 body, 1 + k sub-control k, k < 7). Phase 3 sends and replays body events only; an event for a sub-control is decoded and ignored until phase 4.
- **`pose_game`**: `addAnimObserver` installs the one MinHook on `cAnimControl::set` at the first call and keeps at most 4 observers (published to the game thread by an atomic count, like `game_tick`'s move scopes); phases 4 and 7 register theirs independently. `readPose` reads the new fields (`game.h` "state mode: phase 3").
- **`pose_capture`**: `pose_capture_rule::SampleTimer` (33 ms accumulator, 30 Hz at 60 or 30 frames a second, a hitch owes nothing) replaces "every second move". `onNetTick` (net thread) resends the last sample with `held` at 4 Hz once 250 ms pass without a sample (menu, door, load), with a fresh sequence and owner clock, same room and load serial, so the receiver can tell "owner paused" from "lost".
- **`puppet`**: active = state mode, remote-owned, Control Remote and a peer present (before: also needed a first pose). Before the first pose, while the owner is in another room and while the stream is stale it holds with the pause bit and writes nothing.
- **Trace lines (`adapter.log`).** `puppet: Billy timeline reset (serial|room|gap|teleport|lead|depth|clock)`; `puppet: Billy stale, holding`; `puppet: Billy fresh again after N ms` (N counted from the stale line); the once-a-second `puppet:` line gains `delay Dms, poses buffered N` (D = the newest pose's lead over the shown time, about 100 + jitter).
- **`tools/echo_peer.py`** shifts POSE_STATE's x at byte offset 8 (v2 puts the sequence before the position).
- **Live gate (one PC, ECHO setup, `--offset-x 150`).** Walk through a door: exactly one `timeline reset (serial)`, no slide of the puppet across the room. Open the inventory 5 s: F8 `puppet poses in/s` falls to about 4 and no `stale` line. Stop `echo_peer.py` for 3 s and restart it: `stale, holding`, then `fresh again`. Run in a straight line: `teleport` never logged (else raise `kTeleportUnits` above the distance a `teleport` line implies; probe E1). F8 `puppet poses in/s` about 30 at 60 fps and at a capped 30 fps. `partner_mode=input`: no `puppet:` or `timeline` line, F8 `state refused` 0.

## State mode: room authority (phase 6 of the state-replication plan; built and unit tested, not run live)

Who runs the enemies of a room in `partner_mode=state`. With `partner_mode=input` none of it is enabled and `control_rule::runsEnemies` through `door_travel::enemyAuthority` decides as before.

- **Table.** DS2's pure `authority::AuthorityTable` (`adapters/ds2/src/authority.cpp`, `reject_counters.cpp`, compiled into `re0_adapter` and `room_authority_test` with the include path `../ds2/src`; no DS2 file changed). One record per scene id {owner slot, epoch}. A new record starts at epoch 1; every change adds one. Rules: a claim with a newer epoch replaces the record; two claims of one epoch settle on the lower slot on both machines (the host is slot 0); STOP and DECLINE must carry the current epoch and leave the room unowned at epoch + 1; a leaving slot's rooms become unowned at epoch + 1.
- **Wire.** ROOM_AUTH_CLAIM 0x0166, ROOM_AUTH_DECLINE 0x0167, ROOM_AUTH_STOP 0x0168, all reliable to all, registered with `frame_router` as `Any` (the table's own sender rules judge them), payload `AuthMessage` {u64 scene id, u32 epoch, u8 owner, 3 reserved} (16). The table speaks DS2's kinds (0x0111..0x0113, which are other messages in RE0 and never sent); `room_authority_wire::tableKind` maps at the boundary. `decode` also refuses a scene id of 0xaf or more and an owner slot of 8 or more. DECLINE is accepted but this build never sends one.
- **Claim and release** (`room_authority_rule::reconcile`, once per game tick): a room that is unowned and loaded with the own character in it is claimed (the host before the peer has joined plays its chosen character, `plannedLocalCharacter`); a room this machine owns and the own character is not in (left it, or the room is loading) is released. The second arrival finds the room owned and observes. A refused message is counted (`reject_counters`) and logged.
- **Session** (`room_authority::onSession`, net thread, every tick): a new connection or session epoch clears the table; a peer that leaves or is replaced on its slot (new join serial) has its rooms freed (`peer left`); a new peer is sent this machine's claims; `join_sync` also repeats them when it sends (host) or applies (guest) a join snapshot. Without a linked session `runsHere` answers true (vanilla).

## State mode: flags (phase 14 of the state-replication plan; built and unit tested, not run live)

With `partner_mode=state` the host orders story flag changes; `partner_mode=input` keeps FLAG_DIFF 0x010C exactly as shipped (nothing is registered, `flag_sync` runs its old send and receive).

- **Messages.** FLAG_PROPOSE 0x0175 (guest to host, reliable, GuestOnly): the `flag_diff` changes the guest made natively, same payload as FLAG_DIFF (u16 count, u16 reserved, changes). FLAG_COMMIT 0x0176 (host to all, reliable, HostOnly): u32 serial, u8 origin slot, u8 reserved, u16 count, changes. Decoders refuse a wrong size, more than 0x47 changes, a word outside the bitset and a bit both set and cleared. In state mode FLAG_DIFF received is ignored.
- **Local changes.** `flag_sync::onTick` still diffs the live flags against the last agreed ones every 6 frames. In state mode the diff goes to `flag_sequencer::submitLocal` instead of FLAG_DIFF: on the host it is committed at once (next serial, origin = host); on a guest it is proposed (the setter already ran natively, nothing waits for the answer).
- **Host.** `flag_sequencer::collect` takes the queued proposals in arrival order, keeps only the bits that change the host's flags (`effective`, against a model that includes the earlier proposals of the same tick), broadcasts one commit per proposal (an empty one when nothing changed: it is the guest's answer) with origin = the proposing slot, and hands the effective changes to `flag_sync`, which applies them the way it applies a peer's FLAG_DIFF today (setter 0x59bd50 per bit with its side effects, enemy bits raw, BGM refresh 0x643490 after a BGM change). Bits the setter's side effects change afterwards are the host's next local diff and become a commit of their own.
- **Guest.** Commits are taken in serial order and applied through the same `flag_sync` path (bits that already match are skipped, so the echo of the guest's own proposal does nothing). A committed bit that differs from the guest's value while the guest has an unanswered proposal touching that bit is a correction: the committed value is set and `flag_seq: corrected bit 0x%x to %u` is logged (F8 `flag corrections`). A commit answers the guest's oldest proposal when its origin is the guest's slot. The first commit after a reset sets the serial baseline (the join snapshot already holds everything before it); a skipped serial logs `flag_seq: gap %u -> %u, resync`, asks `resync::request` for a snapshot and carries on from that commit; an old serial is ignored. `flag_sequencer::reset` runs when the link drops and after `flag_sync::applySnapshot`.
- **Counters and lines.** F8 `flag commits` (commits with changes issued by the host or applied by a guest) and `flag corrections`; `flag words sent/applied` keep counting guest proposals and applied changes. Log lines: `flag_seq: commit %u (%u set, %u cleared) from slot %d`, `flag_seq: corrected bit 0x%x to %u`, `flag_seq: gap %u -> %u, resync`, `flag_seq: refused a malformed proposal / commit from slot %d`; `flag_sync: received ... flag 0x%x set` still names every applied bit with its family.
- **State mode switch.** `state_mode::enableAll` registers the two types (`flag_sequencer::enable`); the module count in `state_mode: on, %u modules enabled` is now 5 with the phase 2, 3 and 6 modules.
- **Live gate (two PCs).** Normal progress (keys, doors, a cutscene): F8 `flag commits` counts on both machines and no `flag_seq: corrected` line appears. Probe F2: both toggle the same lever-type flag in the same second, ten times: both end equal, `corrected` lines only on the guest.

## State mode: puppet body (phase 4 of the state-replication plan; built and unit tested, not run live)

## State mode: weapon effects (phase 5 of the state-replication plan; built and unit tested, not run live)

How the remote character's shots look on this machine in `partner_mode=state`: the owner records the effect primitives its fire, reload and dry-fire handlers call and the receiver replays them on the puppet. With `partner_mode=input` no hook is installed and nothing is sent.

- **Primitives hooked** (owner side, `weapon_fx_capture`, `state_mode::enableAll`; signatures read in the decrypted image). `sWeapon::playSe` 0x532bb0 thiscall(sWeapon [0xdce0a4]; chara, sound id, f32 volume) ret 0xc; the generic sound 0x532ce0 and the water ripple sound 0x532880 are plain stdcall(chara, id or sub, f32 volume or vec3*) with no `this` (the report's "thiscall" is wrong for these two); `sWeapon::shoot` 0x530ec0 thiscall(sWeapon; player, mat4*, kind) ret 0xc; `player::muzzleFlash` 0x50cb40 thiscall(player; index, f32 scale) ret 8; `sEffect::create` 0x55a6d0 thiscall(sEffect [0xe2da7c]; out*, owner, set, index, attach, joint, pos*, rot*, flags*, extra) ret 0x28, returns `out`; molotov stow 0x50f8b0 and wick 0x50d6e0 thiscall(player), plain ret. The muzzle matrix builder is 0x50e490 thiscall(player; mat4*, muzzle) ret 8.
- **Allow-list** (`weapon_fx_sites.h`): 36 return addresses, every role E row of the call-site table, each checked to be an `e8` call to its primitive: 11 `playSe`, 2 `muzzleFlash`, 6 `sEffect::create`, 9 `shoot`, 1 stow, 1 wick, 2 ripple, 4 generic sound. The site id on the wire is the row index. The muzzle column is the argument the handler passed to 0x50e490 just before `shoot` (1 for every casing, 2 for the reload magazine, 0 for the projectile). Not listed, by design: the hitscans 0x52f520 / 0x52fd10, the melee hit 0x52ef90, Wesker's beam 0x530a50, `spendAmmo` 0x4db9c0, `ItemBlock::reload` 0x4db6b0, the shots counter (think slot 24) and the rumble (slot 15).
- **Capture rules.** Each detour calls the original first; the call is recorded only when the shooter argument (or `this`; for `sEffect::create` the owner, which must be the owned character or its weapon unit at +0x6838) is the character this machine owns, it is the outermost hooked call on its thread (a shoot, a muzzle flash and `playSe` make effects of their own, which are part of it), and the return address is in the table. Any other call by the owned character is counted as unlisted. `sEffect::create` is also called off the game thread, so the unlisted counter is atomic and the batch is only touched from listed sites. An entry the receiver's own decoder would refuse (`weapon_fx_wire::acceptable`, an encode then decode of the single entry) is counted instead of sent, so one odd call cannot make the peer drop a whole message. At the owned character's post-move the batch is sent as one reliable WEAPON_FX (a batch that reaches 16 entries is sent at once); nothing is sent before `join_sync::caughtUp`.
- **Wire** (`weapon_fx_wire.h`, 0x0142, reliable, numbered, via `state_net`, router policy Any, accepted only from the driving peer): header 12 bytes {u32 sender ms, u32 seq, u8 character (logs only), u8 count 1..16, u16 pad}, then entries, each starting with its op: sound 8 {op 1, site, u16 sound id, f32 volume}; flash 8 {op 2, site, u8 index, pad, f32 scale}; shoot 4 {op 3, site, kind, muzzle} for a casing (1) or magazine (2); projectile (kind 0) 44 {the 4, f32 pos[3], f32 quat[4], f32 auto pitch (+0x68ec), f32 manual pitch (+0x695c), u32 weapon type}; effect 32 {op 4, site, u16 index, u8 owner (0 character, 1 weapon unit), u8 attach (0 none, 1 character, 2 weapon unit), i8 joint, pad, f32 pos[3], f32 rot[3]}; ripple 16 {op 5, site, u8 sub, pad, f32 pos[3]}; stow / wick 4 {op 6 / 7, site, u16 pad}. The report listed the projectile as 44 and the effect as 32 bytes, but its fields add up to 40 and 36; the effect's last argument `extra` is 0 at every listed site, so it is not sent (32), and the projectile carries the owner's weapon type in the 4 spare bytes (44). The decoder refuses an unknown op, a count past the payload, trailing bytes, a site that is not a row of that op, a sound outside the engine's range (playSe 0x1e00..0x290c, which it asserts on; Wesker's 0xa54..0xa57), a volume or scale outside 0..8, a shoot kind or muzzle over 2, an effect owner over 1, attach over 2 or joint below -1, a ripple sub over 1, a projectile rotation that is not a unit quaternion and any non-finite number. The muzzle matrix travels as position and quaternion (`weapon_fx_matrix.h`; the rotation is split and joined in one fixed layout, so the engine's matrix comes back exactly whichever way it multiplies).
- **Replay** (`weapon_fx_replay`, `weapon_fx_game`). Batches wait on a `timed_queue` against the clock the puppet is shown by (`puppet::clockFor(slot)`, read-only: WEAPON_FX does not feed it); the queue starts over when that clock is re-anchored. From a post-move entry for the puppet (`puppet::active`), the due batches are replayed in order, only in plain gameplay in the loaded room (not during a door, a cutscene, or when the puppet is elsewhere). Each entry calls the same primitive with the puppet in place of the owner: sound and flash directly; a casing or magazine rebuilds the matrix with `0x50e490(puppet, &m, muzzle)`; a projectile writes the owner's two pitches into the puppet first and builds the matrix from the entry; an effect uses the puppet or its weapon unit as owner and attach and the owner's effect set (+0x6790 of the owner), flags {[0xdc20dc], 0x10}. The calls go through the hooked entries and are ignored there (the puppet is not the owned character), so nothing echoes. The puppet never runs the hitscans, melee, ammo, counter or rumble. Every call is SEH guarded (`crash_dump::reportCaught`). A projectile whose weapon type differs from the puppet's +0x6950 is logged (the equip refresh lags), not skipped.
- **Projectile damage fix** (`enemy_damage_hook::onDamage`, one `state_mode::on()` branch). A grenade round, molotov or rocket hits the enemy with the uBullet (vtable 0xcd14a8) as `attacker`, which `character_owner::identify` does not know, so input mode treats it as damage no player dealt. In state mode an Unknown attacker whose `HitInfo +0x10` is a player is that player: the hit goes through `onPlayerHit` like a bullet's (the shooter's machine reports it; the puppet's own copy of the projectile has a remote-owned shooter and is dropped; `applyAsOwner` and HIT_APPLIED replays carry the player, not the uBullet). Friendly fire stays impossible (the hit lists filter by class).
- **Trace lines and counters.** `weapon_fx: sent %u entries (%u unlisted calls skipped)` once a second while anything was sent or skipped; `weapon_fx: Billy replayed %s site %u` once per site per session (a failed call logs `weapon_fx: Billy %s site %u failed`); `weapon_fx: Billy projectile of weapon %u, puppet holds %d`; `weapon_fx: projectile hit on slot %d by %s`; `weapon_fx: refused a malformed message from slot %u`; `weapon_fx: %u stale messages dropped`. F8 `fx out` (entries sent), `fx in` (entries received and accepted), `fx unlisted`. The two weapon effect modules count in `state_mode: on, N modules enabled` (9 with all merged phases).
- **Live gate, one PC with the echo peer** (`partner_mode=state`, `tools/echo_peer.py --offset-x 150`, which now echoes WEAPON_FX and shifts its positions): Rebecca fires the handgun, shotgun, the three grenade rounds, magnum, SMG, molotov and the knife; about 1.1 s later Billy shows the flash, sound, casings, the reload magazine and the projectile, nothing doubled. Proof: `weapon_fx: Billy replayed ...` lines for the sites that fired, F8 `fx in` equals `fx out`, `fx unlisted` small and steady (footsteps and other effects of the owned character land there; a burst while firing names a missing row). Probes W1, W2, W4 (STATE_PLAN 5.2): equip each weapon with `player_fields_probe.py` running (+0x6950 per item); each weapon once, molotov and grenade at a wall marker, repeat in room 0x32 or 0x67; a zombie that has not noticed anyone turns when the guest shoots. **Two PCs, probe W5:** the guest fires one grenade round into a zombie in the host-authority room: the guest logs `weapon_fx: projectile hit on slot N by Billy`, the host applies it once, the zombie's HP drops once on both.

## State mode: enemy observers (phase 7 of the state-replication plan; built and unit tested, not run live)

In `partner_mode=state` the machine that runs a room (the room authority, phase 6) is the enemies' only simulator; the other machine shows the room's Observer-class enemies from streams, animated by the engine's own CharPause path. With `partner_mode=input` none of it is enabled: `state_mode::enableAll` is the only place that registers the types, hooks the unit move and adds the capture, and every edit to an existing module is one `state_mode::on()` branch.

- **Engine facts (read in the decompile this phase).** `0x526b30` is slot 8 of every unit (fastcall, no stack arguments). With sGameInfo +0x50 bit 0 set (`0xa885b0` returns `sGameInfo + 0x50`; test at 0x526c7d) and the unit's DTI id (`+0x1c` of the object slot 4 returns, low byte) not in {3, 7, 8, 9, 0xb, 0xc, 0xe, 0xf, 0x77} it runs only slot 31 (`0x5286c0`, motion update), `pos -= mDeltaPos` (+0xed0), slot 18 and slot 19 and returns; otherwise it jumps to slot 41, the class update. None of the 38 enemy classes has an id in that list (they are 0x10..0x6b), so the pause applies to all. `0x521ac0` / `0x521b00` (behind the uEnemyBase motion setters 0x4cc280 and 0x4cc370) do `add ecx, 0xff8` before `cAnimControl::set`: an enemy's anim control is at +0xff8 like a player's. `setHP` 0x529310 is a plain store to +0x1030; `0x528ee0` / `0x528ec0` are plain or / and-not on +0x16ec (low 10 bits).
- **Roles, once a frame (`enemy_observer` tick).** `observing` = a peer is present, the two share the loaded room and `room_authority::holderOf(scene)` names the peer; `simulating` = the same with this machine as holder. A change of scene, holder or epoch drops every slot's state and the queued batches (`enemy_observer: showing scene 0x%02x from slot %u e%u` / `stopped showing scene`).
- **Simulator** (`enemy_observer_capture`). A `cAnimControl::set` observer (one of pose_game's at most four) queues the requests of Observer-class pool enemies; once a frame they leave as ENEMY_MOTION 0x0161 (reliable, batched). A 20 Hz round (`SampleTimer` with 50 ms) sends ENEMY_POSE 0x0160 for every Observer-class pool enemy that has a known spawn: living ones and, once a second, corpses unreliably; a death once more reliably with `terminal`; a unit that left the pool (or another enemy in its slot) once reliably with `removed`. `enemy_observer_send_rule::SendPlanner` decides per slot.
- **Wire.** Header 16 bytes {senderMs, batch seq, roomEpoch, scene, count, pad}; pose entry 60 bytes {slot, class index (position in `game::kEnemyVtables`), flags alive 1 / terminal 2 / removed 4 / leased 8, target, spawn id, spawn record, hp i16, hit attributes, position, rotation smallest-three, motion 0 and 1, frame 0 f32, frame 1 in 1/64, record x4 from +0x67a4, +0x6a0c}; motion entry 20 bytes {slot, layer, motion, flags, interp, start, dtMs before the header time, low 16 bits of the request number}; at most 18 entries per packet. `static_assert` sizes; decoders refuse wrong sizes, counts, scenes (>= 0xaf), slots (>= 37), classes (>= 38), unknown flags, targets, a lease token that does not match the leased flag, non-zero pads and non-finite numbers. HP is clamped to 16 bits.
- **Which batches count.** Only from the slot that `room_authority::holderOf(loaded scene)` names, for the loaded scene, with that table epoch (`refusalOf`); anything else is counted (`enemy_observer: batch from slot %u refused (sender|scene|epoch)`). Entries go to the slot only when the local enemy there is an Observer-class enemy of the same class index and spawn id (`bound`).
- **Spawn identity.** `enemy_spawn` (state mode) remembers, per pool slot and enemy pointer, the spawn record index and the low word of the record's spawn id (+0x10) that the create used; both machines create from the same records. This replaces the plan's `+0x67c4` as the id: +0x67c4 is written only by the base family's spawn init (0x41ea80), so other classes would compare an unrelated field. An enemy created outside the hook has no origin and is neither sent nor observed (it keeps the input-mode paths).
- **Observer unit move.** The MinHook on `0x526b30` is a pass-through for players and for every enemy that is not scoped. A scoped enemy is an observed one whose record word 0 has left setup state 0 (`ConstructionGate`: construction runs natively, and the gate closes again if a re-created enemy shows state 0) and that the simulator has not removed. Before the original move: the shown sample is written (position and rotation; HP through setHP only when it differs; the four record words only when word 0 is past setup; hit attributes without touching the upper bits; +0x6a0c), motion requests due on the shared clock are replayed through the original `cAnimControl::set` after the bank check 0x73e650 (a miss is counted and skipped), layer 0 is seeked to the simulator's motion and frame when it has drifted (`puppet_rule::SeekTracker`, 6 frames for 6 moves, immediately after a timeline reset); then the CharPause bit is set for the one original call and restored as found.
- **Hold, never decide.** No data, a stale stream (2 s), no clock yet or a binding mismatch keeps the scope on with the last motion; the 15-tick "think for itself" rule and the follower target override never apply to an observed enemy. Hand-over to the new simulator when the authority changes is phase 8 (until then an enemy that stops being observed simply runs its own update again).
- **Timeline.** `SlotTimeline` per enemy on the peer's `StreamClock` (shared with the puppet through `puppet::clockFor`, 100 ms behind): position and rotation interpolated, frames on the same motion, every discrete field (flags, hp, record, motions, attributes, +0x6a0c) from the older sample, nothing extrapolated, past the newest sample the last one is held. Hard resets (placed at once, seek requested): a sender or arrival gap over 500 ms, a jump of 2000 units, a clock re-anchor; a corpse's once-a-second samples are no gap. `Lead` / `Depth` are not repeated here: they re-anchor the shared clock in the puppet's timeline and the enemies follow its generation.
- **Death and removal.** A shown sample with `terminal` writes HP <= 0 and the stream's death motion plays; `removed` clears the scope for good (`enemy_observer: slot N removed`), so the class's own update takes the unit out (probe X4).
- **Edits to the input-mode design (state mode only).** `enemy_decision`: an observed enemy's think step and executors run natively (nothing replaced). `enemy_state`: an observed enemy is not aligned or followed. `enemy_net`: HIT_APPLIED (and the "damage no player dealt" outcome) for an observed enemy is not replayed; HIT_REQUEST still goes to the simulator. `enemy_target` needs no edit: its follower override is fed only by `enemy_state`'s alignment, which skips observed enemies. Legacy and Native classes are untouched. The simulator still reports ENEMY_DECISION / ENEMY_STATE as before.
- **Known gap until phase 9.** The simulator's enemies cannot hurt the puppet (slot 34 is refused), so the non-authority player takes no enemy damage.

## State mode: item ledger (phase 12 of the state-replication plan; built and unit tested, not run live)

With `partner_mode=state` the host decides who takes a floor item; `partner_mode=input` keeps `pickup_guard` and `floor_items_sync` exactly as shipped (nothing is registered, no step is held).

- **Messages.** TAKE_REQUEST 0x0170 (guest to host, reliable, GuestOnly): u16 seq, u16 scene (stage << 8 | room), u32 itemId, u32 count, f32 pos[3] (24 bytes). TAKE_RESULT 0x0171 (host to all, reliable, HostOnly): u32 serial, u16 seq, u16 scene, u8 requester slot, u8 answer (0 granted, 1 taken, 2 claimed), u16 reserved (12 bytes); only the requester acts on it. Decoders check the exact size, item id <= 0xff, count <= 0xffff and finite floats. ITEM_USE 0x0177 is not built (below).
- **Where the take is held.** The pickup action step 0x500d00 has phases 0 start (starts motion 0x14), 1 take (waits for the status bit 0x800 of +0x68c4, then opens the item-get prompt through 0x5d75d0) and 2 done. In state mode `pickup_guard` asks the ledger at the first phase 1 step and holds the engine's step (returns 0, the motion keeps playing) until the answer comes, so a normal grant arrives long before the hand reaches the item. Phase 0 resets the hold for the next pickup. The existing "target is gone" abort stays first. The prompt itself is untouched; the item leaves the floor when the player confirms it (`sItemPut::remove`, FLOOR_TAKE as today).
- **The item.** The player's interact target +0x67a0 points at the item's data record (id at +4, count u16 at +8; 0x4ded40 returns the record + 4), not at the uItem. The position for the ledger key is that of the live floor item of that id nearest to the player (`floor_items_sync::locateItem`, reach 300 units). Pointer equality between the record and the uItem's own +0x67a0 (set by `sItemPut::put`) would be exact but is not verified, so the nearest-of-id rule is used; if no item is found the take is not arbitrated (log `pickup_guard: take target not found, not arbitrated`) and runs natively.
- **Host ledger.** One entry per item, keyed by scene, item id and position (same item within 10 units; the plan's `pos / 10` as a distance so no item sits across a cell border). The first request is granted and reserves the item for its slot; a request from the other slot is refused `claimed`; the same slot asking again is granted again (a declined prompt, picked up a second time). A reservation lasts 15 s: the take prompt may be declined, which removes nothing, so a grant that was never used lapses. When the item leaves the floor (the host's own `remove`, or a received FLOOR_TAKE) the entry becomes a consumed entry and every later request is refused `taken`. Any put at that spot (own drop, room script, a peer's put applied here) forgets the entry. The entries are the journal of commits since the last save; `floor_items_sync::clearJournal` (accepted save or load) clears them. Capped at 256, oldest dropped. Serials count every entry made.
- **Host's own take.** `resolveTake` on the host decides locally through the same `decide` function, so a host pickup and a guest request race in one order (arrival at the ledger). With nobody linked a guest's request cannot be sent and the take runs.
- **Guest hold.** One request per pickup (seq is a counter), then each frame the answer is looked up; a refusal ends the action (phase 2, the same path as the vanished target), 2 s without an answer ends it too (`timeout`).
- **Puppet's take.** A FLOOR_TAKE from a peer whose stream clock is ready applies one render delay (`stream_clock::kRenderDelayMs`, 100 ms) after it arrives, in order behind earlier events (`releaseDue`); FLOOR_TAKE has no sender clock (the wire is shared with input mode), so arrival time stands for the sender's. FLOOR_PUT and FLOOR_SNAPSHOT apply at once.
- **ITEM_USE not built.** The brief builds `item_use` only if probe I2 shows the menu can use an item on the partner; it has not been run, so 0x0177 stays reserved and the 0x4dbbe0 hook does not exist. A heal on a remote-owned character remains as before.
- **Counters and lines.** F8 `item takes granted/refused` (host decisions) and `pickup holds` (requests this machine sent); `pickups aborted` also counts refused pickups. Log lines: `item_ledger: take scene 0x%04x item 0x%02x committed to slot %d serial %u`, `item_ledger: take scene 0x%04x item 0x%02x refused (%s) for slot %d`, `pickup_guard: take held for the host`, `pickup_guard: take refused (%s)` (taken, claimed, timeout).
- **State mode switch.** `state_mode::enableAll` registers the two types (`item_ledger::enable`); the module count in `state_mode: on, %u modules enabled` is 9 with the phase 2, 3, 5, 6, 7, 12 and 14 modules.
- **Live gate (two PCs).** Probe I1: both press action on one herb within 100 ms, ten times: one `item_ledger: take ... committed` and one `refused (claimed)` line on the host, `pickup_guard: take refused (claimed)` on the loser's machine, one herb in total. A guest pickup in a room the host is not in commits too (`committed to slot 1`). Probe I4: single pickups on a 300 ms link show `pickup_guard: take held for the host` and then the item, with no second prompt and the bend-down motion playing. Not checked statically: what the loser's character does after a refusal at phase 2 (the vanished-target abort ends the action the same way).

## State mode: enemy hits and hand-over (phase 8 of the state-replication plan; built and unit tested, not run live)

Builds on "State mode: enemy observers". With `partner_mode=input` none of it changes: every edit is one `state_mode::on()` branch, `HitPayload.forwarded` is a byte that was reserved (layout and size unchanged, always 0 in input mode) and `room_gate` still hooks the door.

- **Hits go to the simulator.** `enemy_observer::simulatorOf(slot)` is the room authority of the loaded scene (`room_authority::holderOf`; a lease holder takes over from it in phase 9), unknown while the room is unowned or no session is linked. A local player's hit (`enemy_damage_hook::onPlayerHit`, state branch) calls `enemy_net::routeOwnHit`: `Apply` (this machine simulates the enemy: `applyAsOwner`, HIT_APPLIED to the peer), `Send` (HIT_REQUEST to the simulator's slot, payload unchanged), `Local` (nobody simulates it: the original damage runs on this machine alone). A HIT_REQUEST that arrives is applied only where the enemy is simulated; otherwise it is sent on once to the machine that simulates it with `forwarded = 1`, and a request that already carries the byte, or that finds no simulator, is dropped. With two players the forward matters only while the two machines' tables disagree (a hand-over or a lease in flight).
- **Hand-over.** `enemy_observer_rule::roleChange` compares the loaded room's role each frame (`Role` = observing, simulating, scene, holder slot, epoch). The room we were observing becoming ours is `HandOver`; the simulator gone while nobody holds the room yet (the peer left or walked out and the claim is a frame away) is `Wait`: the world stays as it was, the observed enemies keep their scope and hold their last motion, for at most `kHandOverWaitMs` (2 s) before everything starts over. At the hand-over every scoped enemy leaves the CharPause path (the world no longer observes) and `carryOn` reads its record: HP <= 0 is a corpse (its own update plays it out), a record in the think state (2) or setup (0) lets the class's own think pick, anything else starts again at step 0 through vtable slot 63 (`enemy_decision::startAction`, `enemy_follow_rule::startOf`, word 2 = 0). `seedable` is the rule.
- **Creation on demand.** A living Observer-class stream entry whose pool slot is empty here (`createWanted`) is created by `enemy_spawn::createOnDemand` (paced by `CreatePacer`: 4 a frame, one a second per slot): the same seeded create the room load uses, then what the room load does with each result (room origin at record +0x20 added to the position, +0x4c cleared, `0x619e30` assigns the enemy to the record). The create's ECX (the spawn table) is learned from the newest create of the room (`g_context`, valid while its room record is the loaded one); the record must exist and carry the stream's spawn id. A record that already has an enemy here creates nothing. The pool slot is the engine's choice; when it differs from the stream's slot the log says so and the new enemy holds (its entries are refused by the class / spawn binding).
- **Barrier off.** `room_gate::install` hooks nothing in state mode (`room_gate: off in state mode`); `door_travel`'s ROOM_STATE door-ready flag stays 0.
- **Phase 15 API** in `enemy_observer.h`: `freeze(slot)` holds one enemy under the CharPause scope whoever simulates it (ends with `startAt` or a role change), `snapshot(slot)` is the pose entry of `enemy_observer_capture::entryFor` flagged alive or terminal, `startAt(slot, record)` ends the freeze and carries on from `record` like a hand-over.
- **Engine facts (REA, ghidra provider, the decrypted image wrapped as a PE, 2026-10-19).** The create 0x410bb0 is thiscall on the spawn table (ECX, from the caller) with stack arguments (room record, spawn record index, flags), ret 0xc (Evidence ev_67ce7312b6e464a25e21c0f0d695a7fe5ba23c328d4b0730327fe2aad0e78e3a). The room load's wrapper 0x4109d0 pushes the flags from the global 0xdcf2e4 and its caller 0x61b240(room record) adds record +0x20/+0x24/+0x28 to each created enemy's position, clears +0x4c and assigns it with 0x619e30 (ev_df62e64b27386987c778e506bd605739458699ddb4a51ade1227728d893ac7a9, ev_1d3f31bb97359afba36218975aad8aaa5a512ea6cc0669852eac1906b296e843). The create first asks `0x51fed0` (sGameChara unit table, 16-byte entries, 90 of them) for a unit already built from that record index and returns it (ev_64aa6c128fe82923e3e43396075f3ff544069056fee2ea129e3790b4ec21d1a2), so a repeated create never builds a second enemy; the script spawns (flag setter) use the same sequence through 0x4109f0. The base setAction 0x4cc670 stores the four record words at +0x67a4 (ev_2e9647681d90ae23802ef6166d6fcd52ffdd6418411a0f443cceefdd13b2c28e).
- **Trace lines.** `enemy_observer: authority -> here (scene 0x%02x e%u), %u enemies resumed (%u at step 0)`; `enemy_observer: scene 0x%02x lost its simulator, holding`; `enemy_spawn: slot %u created on demand (record %u)` / `... in pool slot %d (record %u)` / `not created on demand (no create seen in this room yet | record %u is not spawn %u here | record %u refused)`; `enemy_net: hit for slot %u sent to slot %d`; `enemy_net: hit for slot %u forwarded to slot %d`; `enemy_net: hit for slot %u dropped (nobody simulates it | forwarded twice)`; `room_gate: off in state mode`. F8 `enemy hand-overs/created on demand`, `enemy hits forwarded/unrouted`.
- **Live gate (two PCs, probes X4, X5, R1).** (1) The authority leaves a room with live zombies (LEAVE_BEHIND): the other machine logs `authority -> here` with the number of zombies, and they keep going from where they were (no teleport, no restart pose). (2) Both enter a room through separate doors 5 s apart: no `Waiting for partner`, no `room_gate:` hold line, the late machine's zombies match at once. (3) The non-authority shoots a zombie: its log `hit for slot N sent to slot 0`, the authority's `hit slot N applied`, the zombie's HP drops once on both. ## State mode: native rooms (phase 10 of the state-replication plan; built and unit tested, not run live)

With `partner_mode=state` every machine goes through the engine's own doors with its own character and the remote character is a puppet that lives in a room record of its owner's room (a dormant record when that is not the loaded room). `partner_mode=input` keeps DOOR_CHANGE, the follow flag, `split_rooms::takeOver` and the desync heuristic exactly as shipped.

- **Verified in the decrypted image through REA.** REA rejects a raw `image.bin`, so a PE wrapper holding the same bytes at base 0x400000 was opened with the Ghidra provider (analysis scratch only; its functions live in the `.text:` address space). `sRoomControl::changeRoom` 0x610c60 (thiscall scene, entry, flags) calls the room change 0x61e2c0 before it returns, then stores the room control's current object (+0x20) and scene (+0x12c): the post-hook sees the character already in the new record (Evidence ev_123f4805268f9fe2077a2ff143a232b8264f2073f403e39129171b85b6f2f16c). Its only caller is the door thunk 0x552720 (ev_54215dfec8b35bc3dce3675f3c9cbffdac12b837090adfee6e2c1518920e3c75), whose only caller is the sDoorLoad update 0x552300 (ev_db605cb5257527b56b4305a30d1b1c0f51b10c00031427b8f040dffb97468cba). `sDoorLoad::start` 0x552b50 stores scene +0x20, entry +0x24, type +0x34, motion +0x38, `~flag & 1` at +0x41, clears the phase (+0x44) and requests room phase 4 (ev_be20d0f2cf94cece9184c3f3f657c4d24dd9e83ba6bbf17f1b91b5b5ef6e6f22). In 0x61e2c0 the partner moves only when the carry veto 0x61e880 allows it and the follow getter 0x5fb240 is set; with follow 0 the controlled character alone is detached, placed at spot mode 0 of the target record (an existing record gets the re-entry placement 0x61e920, a fresh one 0x61b240 and 0x61eb80) and the old record is released unless the partner is in it (ev_3daa98a16fce6edfffbceaf0f4ef041eccf3c1284e941b9e2d76594123745757). `0x61ed50` (record, player, entry, mode) asserts `entry < 16` and reads the spot at record +0x9aa4 + (entry * 3 + mode) * 0x18 (ev_598078bfd0b18a094ab9152d88173fa9c316dc20d707e66632bfeb7e8060fa95): the wire refuses entries above 15 and spot modes above 2.
- **ROOM_MOVE 0x0150** (owner to all, reliable, 12 bytes): u32 seq, u16 scene, u16 entry, u16 loadSerial, u8 character, u8 mode (the entry spot mode the owner stands on, or 0xff for a placement without a door). Sent from a MinHook on changeRoom 0x610c60 after the original (the door's commit point; `scene::observeLoad` runs first so the load serial is the new room's) and, from a per-tick watch, when the own character's record changes without a door (script, join, zap; entry 0, spot 0xff); the watch also announces the current room to a peer that just arrived. The decoder checks the size, scene < 0xaf, entry <= 15, load serial != 0, a known character and a spot mode 0..2 or 0xff; the net handler also needs the sender to be the driving peer and the owner of the named character.
- **Receiver.** The newest ROOM_MOVE waits in `MoveInbox` (older or repeated sequences dropped, wrap-safe, cleared when the peer goes) until the game is in plain gameplay (`game_state::playing()`) and the puppet is not the camera character; then `scene::move` puts the puppet into that room's record on the owner's spot (leave = into a dormant record, enter = into the loaded record, between = dormant to dormant), and skips the engine call when the puppet is already in that record. Nothing is written into a dormant record: the puppet holds there (its pause bit is held for its own move, nothing else), and the first POSE in the loaded room places it exactly. `puppet::active` is now "remote-owned with a peer present", so the puppet is no longer released when its owner is in another room.
- **Self-heal.** `puppet::ownerRoom` is the room of the newest pose (by sequence). A difference from the puppet's record that lasts 1000 ms in plain gameplay, with no ROOM_MOVE meanwhile, moves the puppet to the pose room (entry 0) and repeats each second while it lasts (rooms the game does not have, a room still loading and demo records are ignored). This replaces the "Room desync" toast and automatic resync, which `door_travel` skips in state mode.
- **Follow flag.** `party_mode` keeps sPlayer +0x40 at 0 in state mode, so the engine's carry never moves a remote-owned character. `door_sync::sharedDoor` is false in state mode, so `room_gate` never holds a door (the barrier is off for every door; phase 8 owns the rest of that file) and ROOM_STATE carries no shared-door flag. DOOR_CHANGE is neither sent nor run (`door_sync::onFrame` ignores it), so `split_rooms::takeOver` is unreachable and unchanged; `beforeLocalDoor` / `onArrival` stay, and so does the local-door guard for a focus on the puppet.
- **DOOR_FOLLOW 0x0151** (door runner to the partner's owner, reliable, 28 bytes): u32 serial, u16 sourceScene, u16 scene, u32 entry, type, motion, flag (the arguments of `sDoorLoad::start`), u8 character, u8 reason (0 team, 1 script: a door started while the room phase is EventDemo, Event or Movie), u16 reserved. Sent right after the runner's own `sDoorLoad::start` when the party mode is TEAM, no TraceOff left the partner behind (`kDoorAlone`), a peer is present and the partner's character is in the loaded room. **DOOR_FOLLOW_RESULT 0x0152** (8 bytes): u32 serial, u8 result (0 commit, 1 busy, 2 other room, 3 no peer, 4 timeout), u8 character, u16 reserved.
- **Judging.** On its game tick the partner's owner answers: no peer, then other room (its character is not in the loaded room, or that is not the source room), then busy (a door of its own running, a script thread it leads, a menu open, a phase other than Main (a script's door also allows Event), a think group other than 0 or a state above 6), else commit. Commit runs `sDoorLoad::start` through `door_sync::runFollow` (the local door path that frees a dormant room holding only the partner's character, without sending anything back) and arms an arrival watch; when the changeRoom post-hook reports the awaited room the own character is placed on the follower spot (`scene::placeBehind`: `spot_rule::modeFor` with the other character counted as in the room, so a follower spot equal to the door spot falls back to the side spot) and that spot goes out as the ROOM_MOVE mode, so the leader's puppet stands on the same spot here as the follower does there. A request waits at most 8 s for a game tick. Two doors in the same second find each other's door running: both reply busy and each machine ends in its own target. The runner times out after 8 s; a rejection or a timeout toasts `Partner stayed`, the only toast.
- **Counters and lines.** F8 `room moves sent/applied/healed`, `door follows sent/accepted/rejected` (accepted and rejected count this machine's answers as the follower). Log lines: `room_move: sent %s -> scene 0x%02x entry %u spot %u serial %u`, `room_move: %s -> scene 0x%02x entry %u (leave|enter|between) serial %u`, `room_move: %s self-heal to scene 0x%02x (...)`, `door_follow: serial %u sent`, `door_follow: serial %u accepted`, `door_follow: serial %u rejected (busy|other room|no peer)`, `door_follow: serial %u partner accepted`, `door_follow: serial %u partner rejected (...)`, `door_follow: serial %u timed out`, `door_follow: serial %u arrived in scene 0x%02x, standing behind`, `scene: 0x%x placed behind at entry %u spot %u`.
- **State mode switch.** `state_mode::enableAll` enables `room_move` (the message handler, the changeRoom hook, the tick) and `door_follow`; the module count in `state_mode: on, %u modules enabled` is 11 with the earlier phases.
- **Not checked statically.** The synchronous record load of a never-visited room on the observer (probe R3), what the camera does when the follower is moved to the follower spot right after its room change, and how often a pose-room mismatch outlives a ROOM_MOVE in practice (the heal line says so). Door types and motions are passed through as the engine's own arguments without bounds.
- **Live gate (two PCs).** LEAVE_BEHIND: the guest takes a door; the host log shows `room_move: Billy -> scene 0x.. (leave)` within one network delay of the guest's door commit and Billy vanishes at that moment; the guest walks back and the host shows `(enter)` with Billy at the door spot; the guest takes doors into rooms the host never visited without a visible hitch. TEAM: the host's door gives `door_follow: serial N sent` on the host and `door_follow: serial N accepted` on the guest, each machine plays its own door, the guest's log shows `standing behind`, no carry and no `room_gate` line; both press a door in the same second: `rejected (busy)` and `partner rejected (busy)` on both, each in its own target, nobody swapped; a split save loads with each character in its room and the self-heal line stays absent in normal play.

## State mode: transport and diagnostics (phase 17 of the state-replication plan; built and unit tested, not run live)

Launcher: a profile key `freshTypes` (re0: `0x0140` POSE_STATE, `0x0160` ENEMY_POSE, `0x0173` PROP_MOVE) puts those message types on their own lane. `partner_mode=input` sends none of them, so input mode is unchanged on the wire; DS2 and SR2 have no key and send as before. Adapter: SLOW_FRAME timers, state mode only.

- **Fresh lane.** `Session.OnAdapterFrame` hands an unreliable frame of a fresh type to `FreshQueue` instead of sending it; the end of the same `Session.Pump` flushes the queue on Steam channel 1 (`TransportChannel.Fresh`). The queue holds one frame per (peer, type): a newer one replaces the unsent one. Reliable frames, launcher-owned frames and every other type are sent at once on channel 0 as before. A burst reaches one pump when the adapter stalls and its TCP backlog arrives together, or when the launcher loop is late (10 ms sleep), so the effect is small on a smooth link and shows only after a hitch. `SteamTransport.Pump` receives channels 0 and 1; the peer budget, slot mapping and the adapter see no difference. `LocalTransport` has one lane and ignores the channel (the queue still coalesces).
- **Why a second channel.** The frames of channel 1 do not queue behind reliable traffic of channel 0 (FILE_CHUNK save transfers, MOTION_EVENT bursts) on the sender, so a late pose is not delayed by a reliable retransmit (RE4P 3.1, 7.4: its own channel per player state, newest wins). Whether Steam's per-channel handling helps on the real link is not measured (the plan marks this phase "measured first"; no game was run): the live gate below decides whether `freshTypes` stays in `games/re0.json`.
- **SLOW_FRAME** (`slow_frame_rule.h`, `slow_frame.cpp`; RE4P 3.5). A frame is the time between two ticks of the controlled player's `uPlayerBase::move` (0x513190, once per frame per player; the hook is the one `game_tick` has used since the first release). `game_tick` wraps each callback, move scope and post-move step in `slow_frame::Scope`; the microseconds go to a column chosen by the registered name (prefix table in `slow_frame_rule.h`: puppet, pose_, state_correction, post_move = puppet; enemy_ = enemies; weapon_fx = fx; event_, door_, room_, split_rooms, flag_ = events; net_, join_sync, resync = net; the rest, move scopes without a name and the time outside the callbacks = other, the game's own work is in the frame time but in no column). A frame of 50 ms or more is logged, at most once per 5 s. The scope is free until `slow_frame::enable` (from `state_mode::enableAll`), so input mode takes no timestamps. Loading screens and menus that stop the player's move end in one long interval and log one line; the numbers tell them apart (all columns near 0).
- **Trace lines.** Launcher log: `Fresh channel: 3 types`, `Fresh channel: N older frames replaced`. `adapter.log`: `SLOW_FRAME 83ms: net 1 puppet 4 enemies 2 events 0 fx 0 other 1`.
- **Tests.** `tools/launcher_tests` (`FreshQueueTests`: newest replaces, other type and other peer untouched, reliable never held, order, profile parsing), `slow_frame_test` (50 ms threshold, 5 s limit, sums reset, name mapping).
- **Live gate (two PCs, Wi-Fi, state mode).** Both launcher logs show `Fresh channel: 3 types`; F8 `delay` stays near 100 ms and the puppet shows no more `timeline reset` lines per minute than the phase 3 baseline; a hitch (alt-tab the game for a second) is followed by `Fresh channel: N older frames replaced` in the launcher log of the machine that hitched; during a game stall `adapter.log` has one `SLOW_FRAME` line naming the column that owns the time. DS2 session unaffected: its launcher log has no `Fresh channel` line.

## State mode: contact and lease (phase 9 of the state-replication plan; built and unit tested, not run live)

Closes the "known gap until phase 9" of "State mode: enemy observers": the non-authority player now takes enemy damage and grabs. With `partner_mode=input` none of it is enabled (`state_mode::enableAll` registers it) and the only edits to existing modules are state-mode branches or a rename: the four paths that asked `enemy_observer::observes` (decision, alignment, hit replay) ask `replicates`, still behind `state_mode::on()`.

- **One funnel, routed.** Every enemy damage and grab on a player ends in vtable slot 34, 0x512570 (`PlayerDamageEntry`; thiscall, `this` = victim, stack: attacker, hit position pointer, kind, level, attacker again; ret 0x14). - **Router** (`player_contact::damageEntryDetour`, a puppet as victim only; everything else passes as before). It acts when the attacker is an Observer-class pool enemy created through the spawn hook (`enemy_observer_capture::entryFor`) that this machine simulates (`enemy_observer::simulatorOf(slot).here`: the room authority, or the holder of a lease). Legacy and Native classes run on both machines and keep the refusal. The reaction state classifies the contact (`contact_rule::classify`): 0..5 flinch, knock-back, knock-down and 17..19 death are plain; 6..16 (held, bitten, carried, pulled, attached, thrown, and the unnamed 11) are paired. `contact_rule::route`: plain is a PLAYER_HIT; paired with no lease on the enemy is a lease when the enemy lives and the victim stands in the loaded room (otherwise nothing is sent: a victim put into a hold without a holder would wait for an enemy that never comes); a repeat on the leased victim is dropped; a second victim of a leased enemy gets a PLAYER_HIT only (class 30; probe G1). The call itself still answers 0.
- **PLAYER_HIT 0x0165** (36 bytes, reliable; `contact_net`). Sender: the enemy's simulator. Receiver: the victim's owner, checking room, the table's epoch, that the sender is the enemy's simulator as it sees it (`simulatorOf`) and that the victim is a character it owns, then ordering hits on a `timed_queue` against `puppet::clockFor(sender)` so the hit lands at the sender's time plus the render delay, when its observer copy visibly reaches the character. When due it checks the class and spawn of the local enemy and that the victim is alive and in the room and calls the original 0x512570 (victim, local enemy, point rebuilt around the local enemy, kind, level, local enemy) through `player_contact::applyToLocal` (SEH guarded). The victim's own think then runs every reaction, `takeDamage` or the death state natively; HP and death keep travelling by PLAYER_STATE / PLAYER_DIED.
- **Lease** (`enemy_lease`, wire `enemy_lease_wire.h`, table `enemy_lease_rule.h`). A paired attack is bound to the victim's own think (the group-2 hold state), the struggle 0x4c8ed0 / 0x4caae0 reads the pad only for the controlled character, the grab command +0x69cc is written by the enemy and read by the victim, and the paired snap needs the enemy next to the victim, so the enemy's simulation moves to the victim's machine for the attack. Nothing hooks 0x4c8ed0, 0x4caae0 or 0x517340; there is no GRAB_CMD or STRUGGLE.
  - *Grant* (authority, ENEMY_LEASE 0x0163, 68 bytes): the router only queues the contact; on the next game tick, with the enemy's update over, `grant` reads the enemy (`grantable`: alive and in an action, the record fits the wire), makes a token (`nextToken`, low 16 bits never 0), sends token, epoch, clock, room, slot, class, spawn id, victim, kind, level, HP, record, pose and hit point, and records an Away lease. The enemy is then shown from the holder's stream: `enemy_observer` gives the slot the scope (CharPause path), the holder's clock (`puppet::clockFor(holder)`) and accepts its poses and motions for that slot only from that holder. The authority stops streaming it (`enemy_lease_rule::streams`).
  - *Start* (holder): the grant is queued; it is checked (room, epoch, sender is the room's authority, victim owned here, no other lease on the slot, class and spawn of the local enemy, victim in the room) and started when the authority's clock plus the render delay comes: the local enemy is placed at the grant pose and HP, the original 0x512570 binds the victim (the paired snap runs against the real local enemy), the slot becomes Held (no scope, `replicates` true: the decision, alignment and hit-replay paths leave it alone) and the granted record starts at step 0 through the class's own `setAction` (`enemy_decision::startAction`). Anything that fails answers ENEMY_LEASE_END Declined; a grant not started within 1500 ms of arriving is declined the same way.
  - *Stream* (holder): the enemy's ENEMY_POSE / ENEMY_MOTION go out as for a simulator (`enemy_observer_capture`), but only for held slots, each pose flagged leased with the low 16 bits of the token in the former pad word (`PoseEntry.leaseToken`: non-zero exactly when the leased flag is set). The authority takes a pose only for an Away lease from that holder with that token, with an HP not above the lease's (and only ever lower) and a displacement of at most 1000 + 12000 * dt units from the last accepted pose (dt = local time since it, capped at 2.5 s).
  - *Hits on a leased enemy*: `enemy_observer::simulatorOf` answers the holder for an Away lease and this machine for a Held one, so a local hit goes to the holder as HIT_REQUEST (payload unchanged, `forwarded` as in phase 8) and the holder runs it as the owner; the zombie's damage function writes grab command 3 (released) on the holder, where the victim reads it.
  - *End* (holder, ENEMY_LEASE_END 0x0164, 48 bytes): `contact_rule::finished` each tick: the enemy died (EnemyDead), the victim died (VictimDied: HP 0 or a death state), or, 300 ms after the start, the record left the granted action and the victim left the group-2 hold states (Released); the enemy gone from its slot is Left. The message carries the reason, HP, record and pose. The authority removes the lease and resumes the enemy at once: from the holder's final state when the hold ran (`carriesState`), otherwise from the state it last showed (`enemy_observer::resume`: pose and HP put back, then the phase 8 hand-over rule: an action restarts at step 0 through the class's setAction, a think state or a corpse is left to the class). The holder's enemy becomes a shown enemy again on the next frame. The authority also ends a lease the holder never answers with a first pose within 1500 ms (Expired) or that went silent for 2500 ms (Silent), and tells the holder (ENEMY_LEASE_END from the authority drops a pending or started lease there). A role restart of the room (peer left, room change, authority change) drops every lease; the enemies this machine had given away carry on from the state they were last shown in when the room is the same.
- **Order of the ticks.** `contact_net` and `enemy_lease` register their game tick callbacks before `enemy_observer`'s, so a lease granted or started in a frame scopes or frees its enemy in the same frame (otherwise the authority's enemy would run one more native frame and could contact the puppet again; a repeat on a busy enemy is dropped anyway).
- **Not built / limits.** No STRUGGLE, no GRAB_CMD, no hook on 0x4c8ed0 / 0x4caae0 / 0x517340 (plan 1.4). A HIT_REQUEST for a leased enemy that arrives at the holder before it started the lease (about 150 to 250 ms after the grab) is forwarded once to the authority and dropped there ("forwarded twice"). A second victim on another machine gets a plain hit only. PLAYER_HIT omits the enemy's pose (the plan listed it): the receiver's observer copy is already shown at the sender's time, and the hit point is relative to the enemy.
- **Deviations from the plan's byte counts**: ENEMY_LEASE 68 (plan 72), ENEMY_LEASE_END 48 (44), PLAYER_HIT 36 (48, no enemy pose, a hit sequence number added for ordering and duplicates). The wire carries the room epoch in every message; the `PoseEntry` pad word became `leaseToken` (wire size unchanged).
- **Trace lines (`adapter.log`).** `contact: slot %u (%s) on %s kind %d level %d -> state %d (plain|paired)`; `contact: hit applied to %s from local slot %u`; `contact: hit for slot %u from slot %u dropped (not the simulator, room or victim)`; `lease: token %u slot %u to slot %d (%s)` (authority); `lease: slot %u not granted (hp %d, record %d,%d)`; `lease: token %u started here (%s held)` (holder); `lease: token %u declined (%s)`; `lease: token %u ended (%s) hp %d` (holder, with the reasons released, enemy dead, victim died, enemy gone, declined, expired, silent) and `lease: token %u ended (%s) hp %d` / `ended (%s), enemy not resumed` on the authority, `ended (%s by the authority)` on a holder; `lease: pose for slot %u refused (hp or displacement | wrong token | not the holder)`; `enemy_observer: %u enemies given away resumed`. F8: `contact hits sent/applied/dropped`, `leases granted/started/ended/refused poses`.
- **Live gate (two PCs, host authority; probes G1, G2, G3).** (1) A zombie grabs the guest's Billy: host log `contact: slot N (uEnemy10) on Billy kind 0 level 0 -> state 6 (paired)`, `lease: token T slot N to slot 1`; guest log `lease: token T started here (uEnemy10 held)`, the guest sees the paired grab and escapes by mashing (`ended (released)` on the guest, `ended (released) hp H` on the host, the zombie resumes on the host); the host sees the same hold on its zombie and the Billy puppet. (2) Grabbed again and the host shoots the zombie mid-hold: host `hit for slot N sent to slot 1`, guest `hit slot N applied` and `ended (enemy dead)`, release on both. (3) A bite costs the guest HP once (HP by PLAYER_STATE on both). (4) A bat or Cerberus plain hit: guest `contact: hit applied to Billy from local slot N`, host `-> state S (plain)`. (5) G2: the guest pulls the network cable for 2 s as a zombie grabs: host `ended (expired)` or `(silent)`, the zombie resumes without looping. (6) G1: a class 30 grabbing both: the second victim gets `hit applied` only. (7) G3: time from the host's `contact:` line to the guest's `started here` on a slow link, 10 grabs. `partner_mode=input`: none of these lines, F8 `state refused` 0.
