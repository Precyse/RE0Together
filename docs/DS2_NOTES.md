# DEATH STRANDING 2: reverse-engineering notes

Roadmap and stages: `DS2_ROADMAP.md`.

## Target design: the host is the world server
- **Initial world sync:** the guest starts from a full snapshot of the host's world: the host's save transferred to the guest's session folder and loaded there (RE0's launcher save sync and save_redirect). Strand content (other players' structures, signs, items) that is fetched online per account must be captured on the host and sent; the guest must not fetch its own during co-op. Open question: which strand content is in the save.
- **Dynamic stream:** the host streams structures (built, damaged, destroyed), world cargo, enemies, BTs, weather and timefall, order and quest progress, facility connections. The guest's game never decides these: local authority is suppressed and the host's events are applied (RE0 guest enemies and flags).
- **The guest is an ally:** runs, carries, fights and picks up; never creates or progresses the world.
- **Guest restrictions (first):** no terminals, orders or quest triggers on the guest (blocked at the interaction check, as RE0's act-on-trigger detour); guest world pickups are requested from the host, which removes the object from its world and confirms before the guest adds it to its rack.
- **Guest as a container:** on the host, the guest's body is a cargo container. First version: an adapter-drawn give/take menu that moves items between the host's and the guest's racks with the game's own add/remove item calls on each side; later, the game's native container/transfer UI on the remote body.
- **Own cargo stays own:** each machine simulates its own Sam's inventory, rack, weight and balance; the partner's load is a visual mirror sent on change.

## Decima reflection (RTTI)
- Every reflected type has a static record in `.data` with id -1 until the factory registers it: `{i32 id, u8 kind, u8 flags, ...}`. Kind 4 = compound. Compound: base count +6, attribute count +7, size +0x10, name +0x40, bases +0x58 (16 bytes each: type, offset), attributes +0x60 (0x38 bytes each: type, u16 offset +8, u16 flags +0xA, name +0x10; a null type marks a category). The attribute count overshoots on some types; the table ends at the first malformed entry.
- `tools/ds2/rtti_scan.py` reads them straight from the exe (12315 compound types) and prints a type with inherited fields at absolute offsets.
- **Fuller schema from odradek (GPL-3.0, ShadelessFox/odradek):** its repo ships `odradek-game-ds2/src/main/resources/types.json` (20106 types, DS2 v1.10.89.0: 13846 compounds, 1559 enums, with field names, types, offsets, flags, enum values, messages). Nothing had to be run against the game. Copy: `G:\coop-scratch\ds2\types\ds2_types.json` (source clone and a JDK 25 under `G:\coop-scratch\ds2\tools`; not needed unless the schema must be regenerated with its RTTI generator). `python tools/ds2/ds2types.py <Name>` prints a class with inherited fields at absolute offsets or an enum's values; also `find <regex>`, `field <regex>`, `at <Name> <hex>`. Checked against `rtti_scan.py`: all 12315 exe compounds are in it, no field offset contradicts, and it adds 49640 fields (our scan stops early on 6961 types, e.g. CountdownTimer: 2 of 6 fields) and 1531 compounds the exe scan does not see (e.g. DSPlayerController). It lists only reflected members: runtime-only offsets such as DSBaggage +0x28 or entity +0x56d0 are not in it.
- The exe also keeps MSVC RTTI (`.?AVPlayer@@`), so class vtables are found statically (`tools/ds2/disasm.py vtable <Class>`) and live objects are named by their vtable (`probe.py dump`).

## Script-exported functions
Decima registers script-callable functions by name ("Player_ExportedGetEntity" / "GetEntity"); the registration code loads the name and passes the function address. `tools/ds2/symbols.py` and the `Player` symbol group (registration at 0x1402534a0) give:

| function | address | body |
|---|---|---|
| Player::GetLocalPlayer(int) | 0x140256070 | `PlayerManager` global at 0x14623DF40; index 0 with the static filter {0, 1, 2, 0} at 0x1441EBEC0 returns `manager + 0x48 + index*8` |
| Player::GetEntity | 0x140268ff0 | `[player + 0x48]` |
| Player::GetLastActivatedCamera | 0x140254b00 | shared lock at player +0x100; camera stack count i32 +0xF0, data +0xF8, 0x80-byte entries; the last entry's first qword points at the camera's WeakPtrRTTITarget (+0x20), so camera = value - 0x20 |
| Player ctor | 0x140253970 | vtable 0x14312c108; PlayerGame ctor 0x140750a90 (vtable 0x143191b68) |

Confirmed live (2026-10-01): `PlayerManager` is a `PlayerManagerGame` (+0x48 and +0x60 both hold the `PlayerGame`), `Player +0x48` is a `DSPlayerEntity`, `Player +0xC8` a `GameViewGame`, `Player +0xE8` the `NetPlayerGame`, `Player +0x30` the `PlayerResourceGame`; the camera stack holds one `CameraEntity` in gameplay.

Local player chain used by the adapter: `PlayerManager -> +0x48 (Player*) -> +0x48 (Entity*) -> +0xE8 WorldTransform`. Camera: `Player -> camera stack -> CameraEntity -> +0xE8 WorldTransform, +0x3D4 FOV`.

**Walking:** each tick the body also gets the peer's velocity through its mover (`Entity_ExportedSetVelocity` 0x14014b5e0 forwards to the Mover's virtual at +0xC8). With `tools/ds2/fake_peer.py` walking a 3 m circle at 1.4 m/s the porter strides in its own locomotion animation: `tools/ds2/out/human-walking-crop.png`. The game window's thread pumps with GetMessage and never reaches PeekMessageW, so it is not the simulation thread.
- **EntityResource::CreateEntity** (0x140169e60, behind the export at 0x140185790): (resource, const WorldPosition*, const RotMatrix*, unused, bool awake, name?, parent?, const {u8 kind; void* target}* context, spawnSetup?). ## Cargo (2026-10-01, live)
- Script exports: `DSBaggageManager_sExported*` (AddBaggageToPlayer, CreateAndAddBaggageToPlayer, DeleteBaggage, GetAllBaggages, ExtractBaggageInfo, BreakBaggage, AddBaggagesToPrivateBox, SendRequest, ...). `Inventory_sExportedAddItemByResource` / `RemoveItemByResource` are registered with the stub 0x1400bd210 (`xor al, al; ret`): compiled out. `tools/ds2/symbols.py` tries both registration shapes (inline, and a per-export helper whose caller passes the function as the fifth argument).
- **Request queue.** The exports do not act at once: each takes the manager lock (manager +0x36738, guard 0x1411e9b80) and appends a 0x30-byte request to the array at manager +0x36610 (count) / +0x36618 (data); 0x1411cd530 serves and clears it on the game's update, so any thread may ask. Entry: +0x0 type, +0x4 u32 cargo kind, +0x8 u64 baggage handle, +0x10 u64 owner key (0 = local player), +0x18 u8 slot kind. Types: 1 AddBaggageToPlayer (0x1411eb540, an existing loose piece of that kind), 2 CreateAndAddBaggageToPlayer (0x1411eb610: `(u32 kind, bool)`; the bool is the slot kind, 1 = backpack), 3 BreakBaggage (0x1411eb770: takes the piece off and plays the break effect), 4 DeleteBaggage (0x1411eb6d0: `(u64 handle)`, takes it off its slot and frees it). At the title screen the queue is not served; requests queued there run once the save is loaded.
- **DSBaggageManager** global at 0x14623EA48 (also the `mov rdx, [rip]` at CreateAndAddBaggageToPlayer +15). Baggage pool: count +0x30 (9216), data +0x38, 0x160-byte DSBaggage entries. Entry: +0x18 handle (`index << 41 | serial`, ~0 when free), +0x38 DSGameBaggageListItem (the kind), +0x40 world position (doubles), +0x83 state, +0x98 the owner slot holding it (0 on the ground). The list at manager +0x80/+0x88 is something else (93 entries in lockers and shelters, none on the player).
- **Owners.** manager +0x24278 count / +0x24280 data: baggage owners (players, vehicles, lockers, ...). Owner +0x18 key (local player = 0), +0x28/+0x30 slots (0x1D0 bytes each, first byte the slot kind, +0x8 the owner), +0x48/+0x50 child owners; 0x141198fd0 finds an owner's slot of a kind, searching children. The local player's own slots (kinds 4-24) hold the equipped gear: boots, skeleton, the backpack itself, weapons in hand, grenade belt, blood bag. Its one child (key 0x3400000000000000) is the backpack: slot kind 1 the main load, 26 the grenade pouch, 25 and 15 more.
- **Kind.** DSGameBaggageListItem +0x20 name (LocalizedTextResource: +0x20 UTF-8 text, +0x28 length), +0x28 description, +0x44 u32 kind id (the same on every machine; e.g. 306656069 Headache Pills, 820679211 Machine Pistol [MP]), +0x50 DSGameCommodityListItem.
- **Give/take (Stage A).** `ds2/cargo.cpp` lists the backpack (pool entries whose slot belongs to the player's child owners) and moves pieces with requests 2 and 4: the giver deletes its piece, the receiver creates one of the same kind. Weapons stowed in the backpack are baggage too and move the same way. Not carried over: damage, contents, order links (orders stay with the host anyway).
- **Ground cargo (Stage A pickups, Stage B drops).** A piece keeps its pool handle when it moves between the ground and a rack (Offload in Cargo Management, then E "Carry on Back"), so a pickup shows as a handle that was loose (slot 0, state 1) and is now in the backpack, and a drop the other way round. Picking up cargo sent none of MsgPickUpIsUsable / IsEnabled / Use / Using, MsgIsLuggingAllowed, MsgIsItemRemovalAllowed, MsgIsMountingAllowed, MsgIsContextualActionAllowed or MsgIsDropInventoryItemAllowed through the entity dispatcher (a logging build), and the use-location gate does not stop it, so there is no "is it allowed" query to hold it at. `cargo_ground.cpp` lets the game act and keeps the two worlds the same afterwards: a guest pickup asks the host (CARGO_PICKUP 0x0104 with kind and spot); the host deletes the same kind within 3 m in its own world and accepts, or refuses (CARGO_PICKUP_RESULT 0x0105) and the guest deletes the piece again with a toast. The host's own pickups go to the guests (CARGO_HOST_PICKUP 0x0106), who delete their copy. Drops go to the partner (CARGO_DROP 0x0107), who places the same kind at the spot once its player is within 300 m (farther away the terrain may not be loaded and a placed piece falls through it). Re-picking your own drop is an ordinary pickup, since the piece now lies in both worlds. A piece goes ground -> hands slot -> backpack (and back) over more than one 500 ms watch, so the watch remembers pieces seen loose or carried for 10 s.
- **Placing a piece on the ground:** the manager's create 0x1411c5c00 (manager, u64* handle out, const info*) with a create info built by 0x140abd190 (0xF0 bytes: +0x10 kind, +0x18 world position doubles, +0x30 rotation, identity by default, +0x60 owner, +0x68 slot kind, +0xE8 handle) and no owner reserves a handle under the manager lock (+0x36738) and queues the info on the pending list (+0x12168); the game builds the piece on its next update, on the ground (state 1) where it settles. This is how `game::placeCargo` works. Start it 0.5 m above the spot: a piece created at the reporter's foot height was below the ground 1.5 m away and fell through the terrain (found at z 75.8). The create returns without a handle when the region gate 0x1411ca860 refuses or the pool is full.
- Paths seen with a logging build on the slot removal (0x141185ca0): E pickup leaves the hands slot through 0x141193040 <- 0x141194174 (the pickup action); Cargo Management's Offload runs 0x1411f2760 (called from the menu at 0x14154a3c9), a transaction over the whole menu state (0x12080-byte frame, lists at +0x12070 / +0x24070); 0x1411f0e10 is a similar transaction that uses the scripted place position (`SetPlacePositionForGroundBaggage` 0x141204630 stores a 0x40-byte transform at manager +0x36698 and a flag at +0x36690). Slot writes: 0x141185b30 adds a piece to a slot (+0x98 slot, +0xA0 slot list), 0x141185ca0 removes it.
- **Partner's load (Stage B, first version):** every player sends its backpack list to all (CARGO_LIST, re-sent on change and every 5 s), and each player draws the partner's pieces as boxes on the partner's back through the overlay (`load_overlay.cpp`, geometry in `load_shape.h`): two wide from 0.95 m up, 0.30 x 0.28 x 0.24 m each, at most 12. No world objects are created, so nothing can be picked up, weighs anything or collides. Limits: drawn over the frame, so it shows through walls; boxes, not the real cargo models. A model mirror would mean attaching the kinds' own meshes to the borrowed body (not looked at yet).

- **Network infrastructure (built 2026-10-03 from `docs/research/MULTIPLAYER_MODS_DEEP.md` sections 2, 4, 5-8; unit tested, NOT run live; payloads and rules in `docs/CONTRACT.md`):** (1) Authority records `{id, owner, epoch}` (`authority.cpp`, `authority_sync.cpp`): `authority_sync::claim/release/decline/isOwner/ownerOf`, host-only `assign/stop/pickOwner`, a change handler for the first consumer; nothing claims anything yet, so on the wire only the re-announce of owned claims on peer-up/RESYNC exists. Records are forgotten on a new session epoch. (2) Timing: `clock_sync` pings every peer (250 ms until 16 samples, then 2 s) and keeps the median offset; `DelayLine<T>` (`delay_line.h`) is the timestamped interpolation buffer (render at now minus 150-300 ms, `AdaptiveDelay`); ANIM_STATE carries the sender time (flag 2) and `anim_sync` only measures each partner's lateness and logs `anim_sync: slot N render delay X ms, round trip Y ms` every 5 s, the remote's animation still applies reports as they arrive. To use the buffer: decode the report, `clock_sync::toLocalUs(slot, sentUs)`, `delayLine.push(local, nowUs(), value)`, and each evaluation `delayLine.at(nowUs())` for the pair to interpolate (position and rotation) or the later sample (graph variables). (3) Pulses: a boolean that goes away and back within 0.5 s is also sent reliably as ANIM_EVENT (at most 8 per report); `remote_animation::applyPartner` writes the received pulse for 100 ms after the continuous state, so a one-frame edge is not lost and cannot stick. (4) FACT_SNAPSHOT: the host keeps the last value of every fact it changed in gameplay (`game::factSnapshot`, cap 16384) and sends it in chunks of 256 to each new peer and to any peer that asks; a guest asks once its gameplay settled. The shared flag `remote_apply::Scope` (`remote_apply.h`) replaces the private one in `world_facts`: every hook of the adapter's own checks `remote_apply::active()`. (5) `PendingQueue` (`pending_queue.h`): messages for objects not loaded yet wait up to 10 s, then are dropped and counted; no module uses it yet. (6) RESYNC (`resync.h`): `resync::request(net, slot, scopes)`; creating `<game>\coop\resync_now.txt` triggers a resync of facts, authority and a full anim snapshot on both machines (the adapter deletes the file). Reject counters (`reject_counters.h`) log `rejects: 0x0111 stale_epoch=N ...` every 5 s while they change. **ds2-tester should check on two machines:** the log lines `fact_sync: snapshot N of X facts in K chunks to slot S` right after a peer joins and `fact_sync: gameplay started, asked the host for a fact snapshot` on the guest about 8 s into gameplay, followed by `fact_sync: applied N facts`; `anim_sync: slot N render delay` settling between 150 and 300 ms with a plausible round trip (and no jump on the host after the guest joins); that animation still plays unchanged (the timestamped payload parses: no `rejects: 0x010A malformed`); `resync: manual request` after creating `coop\resync_now.txt` on one side, with a snapshot logged by the host; and that no reject line grows during normal play.
