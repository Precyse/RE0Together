# Saints Row 2: notes for the 4-player co-op adapter

Full research plan (static, not in the repo): `C:\Users\ahmal\coop-scratch\sr2\NATIVE_COOP_4P.md`. Addresses are for the installed `SR2_pc.exe` (Steam build 1076239 with the Juiced patch; PE time stamp 0x49904C37; image base 0x400000, x86, large address aware). The adapter (`adapters/sr2`) refuses to patch an exe that differs (see "Start-up check").

## Confirmed findings
- All co-op netcode is in `SR2_pc.exe`: GameSpy SDK (redirected to OpenSpy by Juiced's `DFEngine.dll`), game port 4200. No Steam networking.
- The session layer (`pc_multi_session`) is built for 12 players; co-op is the same machinery configured down to 2.
- `net_set_mode` 0x7F6F50 (cdecl, one `int mode` argument, mode 1 = co-op) writes the per-mode limits. Its co-op case stores 2 into `[0xE8C434]` (max session players, store at 0x7F71EC) and `[0xE8C438]` (max players, store at 0x7F71F2); `[0xE8C448]` = 1 connection per player.
- `0x7F91C0` sizes the connection pool (`[0xE8C434]` x `[0xE8C448]`) and packet buffers from those limits; whether it runs before or after `net_set_mode` returns is not known yet (milestone 1 trace logs it).
- Player human pool: 12 slots at 0x2CD0590, allocator 0x9D7C10 refuses an index >= `[0xE8C438]`. `#PLAYER1#..#PLAYER12#` script names and `styletest_pc_MP2..MP12` assets already exist.
- `get_remote_player` 0x9D7BD0 (cdecl, no arguments): first human in the list `[0x217043C]` that is not the local player `[0x21703D4]`; about 700 call sites treat it as "the partner".
- Join: message table rows are `{id, handler, name}`: `join_req` handler 0x815BC0 (host accept/refuse), `join_acc` 0x8162E0 (joiner side; calls queue add 0x810220), `join_deny` 0x8163F0. Queue add 0x810220 (stdcall(session, request); queue count at session +0x7EC, 12 entries).
- Replication baselines (deltacomp) are 1 peer in co-op; milestone 3 switches them to the 8-peer instances (see "Replication"). Partner-singular code and Lua scripts (`REMOTE_PLAYER`) come after that.

## Juiced (DFEngine.dll)
Hooks session create, GameSpy code (0x81A590, 0x8360F9, 0xC1BC76, 0xD2526F), mempools, `lua_load_dynamic_script_buffer`, D3D9. It uses safetyhook and does not touch the co-op player limit. None of the addresses the adapter hooks appear in DFEngine. The start-up check compares each hooked function's first bytes, so a function already hooked by another patch is left alone.

## Adapter (milestone 1)
- Loads as `dinput8.dll` next to `SR2_pc.exe` (the exe imports DirectInput8; no such file ships).
- Files: `<game>\coop\sr2_adapter.log` and `<game>\coop\sr2_adapter.ini` (`max_players` 2..8, default 4; `trace` 0/1, default 1; `partner_experimental` 0/1, default 0, see "Partner logic").

- Hook: `net_set_mode`. Both limits are set to `max_players` by a thunk at the allocator-set activation call inside it (see "Replication"). `max_players` 2 patches nothing but the optional trace.

## Co-op player pools (milestone 1b)
- Live: Juiced's mempool watcher reported "Failed aligned alloc of 16384 bytes in coop_player cpu pool (max pool size 2260992)" with a second guest's data.
- Arena setup 0x51D800 creates every startup pool with `vtable[0x44]` (init 0xBF4A10: base, size, name, ...) on a base inside one arena. Pools that depend on the guest count (shipped for 1 guest): `coop_player cpu` object 0x2773F0C, size 0x228000 (`push` at 0x51E502, base arena+0x24D2450); `coop_player gpu` object 0x2773F68, size 0x1071000 (`push` at 0x51E8A7, base arena+0x10A30000). The cpu pool object links the gpu one (`[0x2773F60]`).
- `coop_allocators` (0x2773FC0, 0x5ADBB0) holds the deltacomp baselines; milestone 3 resizes it too (see "Replication"). The pools are packed in the arena (cpu pool ends where `coop_allocators` begins), so none can grow in place.
- Pool object (bump allocator, alloc 0xC00DB0): name +0xC, base +0x38, size +0x3C, used +0x44, mark +0x48, limit +0x4C (free = limit - used), capacity +0x50. Init also zeroes used and mark.
- Change: just before `net_set_mode(1)` runs its co-op case (which resets both pools), each pool gets a VirtualAlloc block of its current size x (max_players - 1) and the fields above are rewritten like init does. Scaling by guests because the shipped size is for one guest (host + 1). Done once per process; max_players 2 changes nothing. The current size is read, so a size Juiced set stays the base. Identity check at that moment: name and three equal size fields; otherwise the pool is left and the log says why.
- Start-up check also compares the two `push size` immediates.
- Juiced overlap: none of 0x2773F0C..0x2773F5C, 0x2773F68..0x2773FB8, 0x51E500..0x51E506, 0x51E8A5..0x51E8AB, 0xBF4A10..0xBF4A5D appears among the 3100 addresses in `df_sr2_targets.tsv`. Juiced hooks the alloc failure call 0xC00E4A and reads pool objects only to print the error.
- Live log: `pools: coop_player cpu 2260992 -> 6782976 bytes`, `pools: coop_player gpu 17240064 -> 51720192 bytes` (max_players 4).

## Replication (milestone 3)
Design and research tables (not in the repo): `C:\Users\ahmal\coop-scratch\sr2\M3_REPLICATION.md`, `m3_n1_to_n8.tsv`, `m3_peer_index_sites.tsv`, `m3_dc_sizes.tsv`. Corrects the plan: the deltacomp array index is the remote member's session slot (member byte +0x1B0, 0..max_players-1), not a peer count.
- Mechanism: co-op picks the 1-peer (N=1) `deltacomp_state_data_impl` at every alloc/free/free_all site (co-op flag), and forces index 0 at 32 more sites. The game also ships an N=8 instance of each of the 8 bundles (player, npc, vehicle, item, mover, prop, rocket, pipebomb), used by Strong Arm with slot indexing. Co-op is switched to those; `max_players` is at most 8.
- Patches (`replication_switch`, tables in `replication_sites.h`, applied together on the first co-op entry, only when `max_players` > 2):
  - 24 entry jumps: each N=1 alloc/free/free_all starts with `jmp` to its byte-identical N=8 twin (the 8 first bytes of both are checked).
  - 32 branch flips: the `je` (0x74) that forces peer index 0 in co-op becomes `jmp` (0xEB), so co-op reads the member slot.
  - 2 set names: the immediate of `mov edi, "coop-mp"` at 0x7F71D5 (activate) and 0x7F7083 (deactivate) becomes `"deltacomp_sa"` (0xE262B8), the set of the eight N=8 allocators.
  - 8 allocator fields: `+0x2C` (pool pointer source) of each N=8 allocator = 0xFA23A4, so co-op takes `coop_allocators` (which co-op stores in [0xFA23A4]) and Strong Arm keeps "mp sa deltacomp". Identity check first: `+8` = "deltacomp_sa", `+0x2C` = 0, `+0x14` = 0 (idle). The exe's static constructors write these objects, so this runs at the first co-op entry, not at start-up.
- Limit timing fix: the limits used to be raised after `net_set_mode` returned, but the player simulation objects and the player deltacomp pools are sized inside it from [0xE8C438]. The call at 0x7F7220 (allocator-set activation, `E8 BB FA FF FF` to 0x7F6CE0) now calls `limit_thunk`'s naked thunk (pushad, pushfd, write both limits, popfd, popad, jmp 0x7F6CE0), and the post-return write is gone.
- Pool: `coop_allocators` is rebased like the player pools (all three or none, name/size/empty check). New size = S0 + 7,131,240 - 16,320 + 35,160 x M + 7,492 x (M - 2) + 1 MiB (`coopAllocatorsPoolSize`): the N=8 fixed bundles replace the N=1 ones (9,207,000 - 2,075,760), the 2 shipped player elements go (15 x 2 x 0x220), M player elements x 15 x 0x928 come, plus 7,492 bytes per added player. 4 players: 13,225,024 + 1 MiB = 14,273,600. Never "mp sa deltacomp" (it overlaps the city master pool).
- Order inside the `net_set_mode(1)` detour: `coop_pools::resize` (three pools), `replication_switch::enable` (only when the pools were resized; otherwise co-op keeps the 1-peer code), the original. Activation then runs with the limits already raised.
- Start-up check: `code_check` covers the pool immediate (0x51E535), the npc limit store (0x7F71F8), the activation call and the two set-name loads; `replication_switch::sitesMatch` the 24 + 24 function starts, 32 branches and 2 immediates. Any difference: the adapter patches nothing. All of these bytes were also compared with the installed `SR2_pc.exe` on disk (read only).
- Slot guard (trace=1): `member_slots` walks the session member list (session [0x2528C14], list +0x400, next +0x22CC, local +0x408), logs slot (+0x1B0), state (+0x3C) and local flag when they change, and if a remote member's slot is outside 0..max_players-1 puts the 32 branches back to `je` (peer index 0; the N=8 code then serves one peer). It runs on join request queued, slot allocator changes, session pool setup, and every change of the default partner or of a remote player (partner_scope). Without trace=1 there is no guard.
- Juiced overlap: none of the written addresses (24 entries, 32 branches, 0x7F71D6, 0x7F7084, 0x7F7220, 8 allocator fields, 0x2773FC0..0x2774014) is within 16 bytes of any value in `df_sr2_targets.tsv`. Read-only data (0xFA23A4, session pointer 0x2528C14) is referenced by Juiced and only read here.
- Partner-singular code (`get_remote_player` has 707 callers) is milestone 4, next section.
- Expected log, host alone (`max_players=4`, trace=1): `code check: exe matches the supported build`, `replication: 24 entries, 32 branches and 2 set names match`, `coop limits: activation call at 0x7F7220 retargeted`. Entering co-op: the two `pools: coop_player ...` lines, `pools: coop_allocators 5954480 -> 14273600 bytes`, `replication: 24 entries, 32 branches, 2 set names patched; 8 N=8 allocators follow the co-op pool`, `coop limits: max session players 2 -> 4, max players 2 -> 4` before `trace: session pools sized ... inside net_set_mode 1`, then `trace: coop_allocators used <less than 14273600> of 14273600 bytes, player N=8 allocator count 60 block <non-zero>`. With a guest: `trace: session members 2`, then one `trace: member 0x... slot 0 ... ` and one `slot 1 ...` line (local and remote); no `is outside the session slots` line. With `max_players=2`: `replication: off, max_players 2 is the shipped co-op, limits and pools are not patched`.

## Partner logic (milestone 4)
Design and research tables (not in the repo): `C:\Users\ahmal\coop-scratch\sr2\M4_PARTNER_LOGIC.md`, `m4_patch_sites.tsv` (the 55 sites), `m4_cls_core.tsv` and `m4_cls_w1..w4.tsv` (454 classified functions). Everything in this section applies only with `max_players` above 2; with 2 nothing is patched and a 2-player session is the shipped game, a guest leaving mid-mission included.
- The problem: the game treats "the partner" as one person, through `get_remote_player` 0x9D7BD0 (first human in the list [0x217043C] that is not the local player, 707 callers) and 0x8CA380 (first session member that is not the local one). With 3 or more players the machines disagree on who that is, P3/P4 are seen as npcs by identity tests and ignored by holds and by streaming, and a guest leaving fails the mission for everyone.
- `partner_scope` owns both getters (hooks C1, C2). Without an override they answer the stable default partner, the same on every machine: on a guest the host's player, on the host the remote with the lowest session slot. With one remote that is the remote the game would pick. Thunks that must reach every remote loop with a per-thread `Override` set to that remote; the getters answer it meanwhile, so the game's own code runs unchanged for each (`anyRemoteHuman`, `eachRemoteHuman`, `eachRemoteMember`; with no remote they run once with no override).
- Human to member: a player human is owned by its own machine, so the owner slot (byte 0 of the net record at human +0xB0) is the session slot (+0x1B0) of its member. `remote_players` pairs the remote humans and the remote members by that slot, in ascending slot order (a joining member has no human yet). Self-check: a remote human whose owner slot matches no member makes the pairing untrusted, every getter then passes the call to the game (vanilla) and the log shows `partner: human 0x.. owner slot N matches no member` once. Probe A is the first real check of this assumption.
- Sites (`partner_sites.h`, 55 rows, each verified against the exe bytes before anything is written; one difference skips milestone 4, logs it, and leaves milestone 3 as it is): getters C1 C2; chunk loaded around any remote O1, hand-over target and nearest rules O2 O3; join tick J1-J5 (ready when every remote member has a ready human, the dialog names the first joining member, re-sync and look sync for every remote); member left L1 (the mission and the session end only when the last in-game remote left) and pause Disconnect L2 (clears +0x1B8 on every remote); identity tests M1-M6 (any remote player counts as the partner); nearest remote N1-N3; per-remote look sync and asset hold E1-E10; known handles and messages K1-K5 (the activity invite goes to the default member only); mover rider V1; go down D1; vehicles A1-A7; the mission start vehicle exit once per remote B1 B2; the Lua party natives S1-S4.
- Thunk kinds: a hook with all registers saved (`PARTNER_WRAP_STUB`, calls the original through `guest_call::callWithRegs` once per remote), a single register to C++ (`PARTNER_REG_STUB`), call blocks and jump-outs with resume addresses (`sr2_addresses.h`). Float math (nearest) runs under `FpuGuard`; the partner files are built `/arch:IA32` so they never touch xmm registers.
- Differences from the research notes: the vehicle exit block (B1, B2) resumes at 0x6A28B9 and runs the replaced `xor bl,bl` and getter call itself, because the notes' 0x6A28B4 lies inside the 7 patched bytes; `callWithRegs` restores the stack from ebp instead of taking a callee-pops flag; no `partner_logic` ini key (`max_players` 2 is the switch); the `remote_player_getter` entry left `code_check` (site C1 checks it) and `join_trace` no longer hooks the getter.
- Probe-gated sites, patched only with `partner_experimental=1`: B3 and B4 customisation exit passengers (Probe G). They log `trace: probe G: remote 0x.. at x y z ...`. D2 (team wipe) and D3 (downed message) were gated on Probe B and are on since milestone 9: the host and guest logs of 2026-10-13 show remote copies carrying the downed timer +0xF8C (230873, 250920, 181172 while down, -1 after). Without the flag the log shows `partner: 53 sites patched, 2 gated (probe G)`; with it `partner: 55 sites patched, the experimental ones included`.
- Trace (trace=1): `trace: default partner now human 0x.. member 0x..`, and on any change of a member, a remote human, its join flags (+0x1161) or its downed timer (+0xF8C) the member lines plus one `trace: remote human 0x.. owner slot N member 0x../none flags 0x.. downed N [default partner]` line per remote human. The downed timer lines are Probe B's evidence without the flag.
- Expected log with `max_players=4`: `partner: 55 sites match` at start-up, then `partner: 53 sites patched, 2 gated (probe G)`. With `max_players=2`: no `partner:` line.
- Juiced: none of the 55 sites is within 16 bytes of an address in `df_sr2_targets.tsv` (unit test `partner_sites_test`, data in `tests/juiced_targets.h`).
- Left for later (cosmetic): partner HUD and names, kick menu, activity roles, respawn wait timers, the `[0x21603CC] == 2` population budgets. Mission participants and Lua `REMOTE_PLAYER` are milestone 5.

## Player cap (milestone 5)
Research (not in the repo): `C:\Users\ahmal\coop-scratch\sr2\M5_PLAYER_CAP.md`, `m5_patch_sites.tsv`.
- "1/2" in the server browser is the session info maximum (+0x38). The builder 0x82FD10 sets it to 2 for co-op (`and ebx, imm8` with imm8 F6, then `add ebx, 12`) and never reads the limit globals. Every full check reads that field: the host's `join_req` handler 0x815BC0 (`join_deny` reason 3, shown as session full), member add, the "joinable" checks, the QR2 `maxplayers`/`open_slots` keys and the guest browser filter.
- P1 (`session_info_max`, 0x82FD81): the imm8 at 0x82FD83 becomes (`max_players` - 12) and 0xFF (F8 for 4). Written at init, before a session exists; a session keeps the maximum it was created with. Guests copy the host's value.
- P2 (`coop_member_count_test`, 0x7F7AFD): isCoop required exactly 2 members (`cmp [ecx+0x30], 2`), so with a third member co-op was off on every machine. The 6 bytes become `jmp` to a thunk (`player_cap.cpp`, `remote_players::anyRemoteMemberAtLeast`) that answers 1 when a member other than the local one has state >= 0xB. With 2 members it is the shipped test; a member still joining is ignored, so a third join does not drop co-op for the two already in.
- Both edits are checked and written together (`player_cap::install`), only when `max_players` > 2. Neither is within 16 bytes of a Juiced target (Juiced only calls isCoop).
- Log line: `player cap: session maximum 4, isCoop counts ready members`; `player cap: sites differ, the maximum stays 2` when the bytes are not the supported build's.

## Join trace (milestone 5b)
The third player's join stalled at "please wait" with no new member on the host. Research: `C:\Users\ahmal\coop-scratch\sr2\M5_PLAYER_CAP.md`, section M5b. With `trace=1` the adapter byte-checks 12 sites and logs (all lines start `trace:`):
- Host: `nat request, cookie, negotiation running` (T1, 0x8CFDE0); `nat negotiation complete, result (0 ok), cookie` (T2, 0x8CC1F0); `message join_req|join_acc|join_deny|join_new_session ... mapped member` for join messages reaching the dispatcher (T3, 0x8138F0, since milestone 9 logged by the sender scope hook of that address, `sender_scope.cpp`); `join_req handler, name, sender words, session members/reserved/max` (T4, 0x815BC0); `join_req dropped, the sender is already mapped` (T4a, 0x815BEB) and `... a member has the sender's address` (T4b, 0x815EB5), the two silent drops; `join_deny sent, reason` (T5, 0x816F60); `member add returned N, busy state, join type, counts` (T6, 0x80F640: 0 ok, 3 full, 4 invite only, 5 busy); `member allocated 0x..` (T7, 0x7F9590, 0 = pool exhausted).

B1 to B3 of the research (skip a refusal) are not applied. B3's site (0x815EB5) is T4b's: applying B3 means giving up that trace line.

## Game port (milestone 5e)
Guests behind one NAT all bind local UDP 4200; the router can keep that external port for one of them only, so the NAT negotiation of the next ones ends with result 3 (ping timeout). Research: `C:\Users\ahmal\coop-scratch\sr2\M5_PLAYER_CAP.md`, section M5e.
- Ini key `game_port` (default 4200, valid 1024..65535, anything else is ignored and logged). Hosts stay on 4200: joiners assume host:4200.
- E1 (0xC1BBAF, `mov eax, 4200` in the socket bind): the immediate becomes `game_port`, only when it is not 4200.
- E2 (six `mov word ptr [reg+4], 4200` at 0x811AC0, 0x811B11, 0x811BA4, 0x811C0D, 0x811C7A, 0x811CB7): our advertised record port, same rule.
- E3 (0x8CDA3B, the quick check for a peer behind our public IP): a thunk keeps 4200 for the session host and the port the host relayed for anyone else.
- E2 and E3 follow the `max_players` > 2 gate. All eight sites are checked together before anything is written. `trace=1` logs the port, whether E1 was applied and each quick check.
- H1, H2 (milestone 5g, with `max_players` > 2): guests behind one home network reach each other by the peer's local port, but the host only knows each guest's external source port. H1 (0x815D8C, join_req handler) remembers the local port a guest reports before 0x815D97 overwrites it with the real source, keyed by the real source IP and port; H2 (0x815666, the new_conn record builder) writes that port into the record (buffer + offset + 13) that the other guests get. The host's own member records keep the external source. E3 then uses the guest's local port. T11 (0x813BF2, `trace=1` only) logs the first unmapped sender from each private range address.
- L1 (milestone 5g, with `max_players` > 2): every peer reports `h_addr_list[0]` of its host name as its private IP, and a VPN or virtual adapter is often listed first; a wrong one breaks the direct path between two guests behind one router. The five gethostname / gethostbyname pairs (0x810C94 the game's record, 0x7F79D0 the second local IP getter, 0x8E1B3E GameSpy's localip list, 0x8D7C00 GameSpy, 0xC1C0FE the net library) go to one thunk, together or none (a partial set made the host's record and its `localip0` disagree, M5f). The thunk calls the real function and, only for the machine's own name, swaps the chosen address to the front (never overwrites; an address not in the list changes nothing). The adapter is chosen once per process: up, IPv4 gateway, RFC1918 address, Ethernet or Wi-Fi, name and description not Radmin, Hamachi, ZeroTier, Tailscale, WireGuard, OpenVPN, TAP, Proton, VirtualBox, VMware, Hyper-V, vEthernet, WSL or Npcap, lowest IPv4 metric; none qualifies means no change. `trace=1` logs the adapter and address.
- Live test: player 3 with `game_port=4201`; expect "nat negotiation complete, result 0" and a `join_req` from the router's address with port 4201.

## Late joiners (milestone 5h)
A newcomer never got the human of a guest that was already in the session. The member state change callback (0x8CB840) queues every object the host owns for a member that becomes ready (0x8051F0, EDX = member), and sends the look sync, only on the host; in the shipped 2-player co-op only the host owned objects that existed before a member joined. Objects created after a member exists reach it through normal replication, which is why a guest that joined later was seen. Research: `C:\Users\ahmal\coop-scratch\sr2\M5_PLAYER_CAP.md`, section M5h.
- G1 (0x8CBA34, `83 7F 3C 0D 75 0D`, the guest branch of the callback) jumps to a thunk, applied with the other M5 edits (all peers, `max_players` > 2). A welcome is two steps. ## Version gate (milestones 8 and 11 B3)
Only peers running the same mod build play together. Research: `C:\Users\ahmal\coop-scratch\sr2\M8_VERSION_GATE.md`, sites `m8_patch_sites.tsv`.
- Every join_req and join_acc a modded peer sends ends with a 16-byte trailer (milestone 11 B3; 8 bytes up to protocol version 2): u64 LE content hash, then the milestone 8 trailer unchanged, `CFVG`, u16 `version::kProtocolVersion` (version.h, bumped whenever the wire behaviour changes), max_players, flags (bit 0: partner_experimental sites patched, bit 1: steam transport). ### Fast fire (milestone 11 B1: CK1, CK2, BUT)
Research: `C:\Users\ahmal\coop-scratch\sr2\M11_SHATTERED_IDEAS.md`, section 1. Live report: on player 3's screen the other players' guns and the NPCs' guns fire too fast, player 3's own gun is fine, player 2 (also a guest with two remotes) saw nothing.
- Why the clock: every replicated object (players and NPCs) replays its input history against one value per session, the net clock T (`[session+8]`). Two things write it: the net tick 0x7FC930 adds the frame time (`[0x212B15C]`, at most 250 ms) to every session, and the `clock` message handler 0x7FCBF0 **sets** `[session+8] = payload + [sender member+0x223C]` (half the sender's round trip) from any sender, backward as well as forward. A step back of D ms replays the last D ms of every history, and each replayed release and press re-arms an automatic weapon's deadlines, so a copy fires faster than its refire. The fire chain of the local player never reads T, which is why player 3's own gun was fine. FE1 (fire bits kept monotonic per remote player) of the research is dropped: it covered players only.
- Rule (`net_clock_rules.h`): on a clock message the target is `payload + half rtt`. A clock from a member that is not the host (`[session+0x404]`) is ignored (logged). A target at or ahead of T is taken, as the game does. A target behind T leaves T and becomes a debt of `T - target`. After each tick that advanced T by A ms, `min(debt, A / 2)` is taken back off T, so T still advances at least A / 2 and never steps back. A debt above `kMaxClockDebtMs` (1000) is a real resync: T is set as the game would and it is logged. The tick's advance is measured as T before and after the game's tick (the tick recomputes `[0x212B15C]` for the next frame at its end, so that variable is not the frame time just added) and counts only when it is at most 250.
- CK1 (hook 0x7FCBF0, cdecl(payload, context), sender `[ctx+4]`, session `[sender+0x1AC]`) and CK2 (hook 0x7FC930) apply it only on a guest with two or more remote members, with the other `max_players` > 2 phases. The host, a guest with one remote (2-player play under `max_players` 4) and `max_players` 2 run the game's code.
- `trace=1`: `trace: net clock: from slot S, payload P + half rtt R = target X, ours T, step D ms, debt B` for every clock message (about one a second); a step of -D with D of 33 or more on player 3 together with fast TF1 gaps confirms the clock as the cause. Always: `net clock: ignored a clock from slot S, which is not the host` and `net clock: resync, ours was D ms ahead of the host` (at most one a second).
- BUT (`trace=1`, pointer swap 0xE2B454, the player bundle's unpack 0x8669D0, thiscall(handle, ...)): `trace: bundle: handle 0x.. owner slot O updated by slot S` once per handle and sender when the sender (`sender_scope::currentSender`, set by SS1 and SS2 around the handler) is not the owner of the object. The unpack does not compare the sender with the record's owner; this line exists to tell an ownership disagreement from the clock. If it fires, the fix is a gate at the unpack (built only then).
- TF1 now also logs `local player 0/1` (the human is `[0x21703D4]`) and `npc 0/1` (not in the static player pool 0x2CD0590, 12 x 0x18F0), so the same log shows whether NPC guns share the fast gaps (the clock) or only some owners' objects do (BUT).

### Cutscenes (MC1, MC2, CS1, CS2; CE3 to CE5 trace=1 only)

### Pause flag (N4)
- The pausing handler 0x8CB110 (message 0x80, broadcast by 0x8CB140) stored `[0x252932F] = byte != 0` from whichever remote sent it, then tail-jumped to the apply 0x8CA190 on every message once the local member was in game (state 0xD); the member left prologue (0x8CB28E) and the session lost handler cleared it. The readers (0x8CA1F0, 0x8CB1B7, 0x8CB28E, 0x8CB8B4, 0x8CBA79) only test it for zero. With several players the last message won and any leave cleared it.
- The apply 0x8CA190 is not a resume. Byte set: it pauses the world (`pause_world` 0x7540D0 with remote = 1, which calls 0x699840 with reason 3), or the overlay (0x699840 with reason 0x10) when the local player is in a menu. Byte clear: it unpauses (0x754270, 0x699910 with reason 3, or 0x699910 with reason 0x10). 0x699840 is reference counted (`[0x2527C08]` += 1, `[0x144E9A0 + reason]` set; 0x699910 takes one) under the critical section 0x27AC4B4, and the world runs only at count 0. With one remote every message is a transition (1, 0, 1 ...), so the counts balance; with a mask any message that leaves the byte set (a second pauser, or the same player sending 1 twice from a pause menu and a reason 5 or 0xB menu) adds a count that the final clear never removes: the menu goes away and the world stays frozen (live 2026-10-18, three players, steam transport: host and P3 frozen for good).
- The byte now holds a bit per session slot (slots 0 to 7; a higher one shares bit 7) and the apply runs only when the byte goes between zero and not zero (`pause_mask_rules::afterMessage`, `afterLeave`: `Change {before, after, apply}`). N4a (JUMP_OUT, 13 bytes at 0x8CB12A: the store, the `jl` and the tail `jmp 0x8CA190`; nothing branches into the middle) enters `PARTNER_WRAP_STUB` `pauseMessageStub` with the frame of a function entry: `args[1]` is the context (`[ctx+4]` the sender member, its slot at `+0x1B0`), `regs.ecx & 0xFF` the paused flag, `regs.eax` the local member (`+0x3C` its state); the stub returns to the dispatcher (both ignore the handler's eax). A message before the local member is at state 0xD changes the byte only (0x8CB840 applies it on reaching 0xD, as the handler's own `jl` did). A message without a sender member is logged (rate limited) and ignored. The first N4a was a CALL_BLOCK whose hand-written stub pushed `[esp+48]`, which is the payload and not the context, so the slot was read from the bytes after the message. N4b (the 21 bytes at 0x8CB28E, ebx = the leaver) is the member left dispatcher `member_left.cpp`: `pause_mask::afterLeave` clears the leaver's bit and applies on the same edge (the resume stays before 0x8CB2A3, whose reason 9 logic reads the count right after it, as the shipped game has it), `cutscene_sync::memberLeft` follows. A session lost still writes 0 and applies once; N4b finds nothing to clear then, or the other way round. With one remote the byte is zero or not exactly as before, except that the same player sending 1 twice no longer adds a count.
- `trace=1`: `pause: slot S sent B, mask 0xAA -> 0xBB, local state N, apply|no change`; `pause: slot S left, mask 0xAA -> 0xBB, apply|no change`; `pause: apply 0x8CA190 with mask 0xBB: count C -> D, world paused X -> Y, remote pause R -> R'` (`[0x2527C08]`, `[0x2527FDA]`, `[0x2527FDB]` before and after). Always: `pause: message 0x80 without a sender member, ignored`. A good run ends every pause episode with `count 1 -> 0` and `world paused 1 -> 0`; a count that stays above 0 after the last apply is the leak again. `max_players` 2 does not install the phase, so the exe is byte-identical.
- Live gate (three players, trace=1 on all): each player pauses and unpauses in turn (the `sent` lines name slots 0, 1, 2, every episode ends `count 1 -> 0`); P2 and P3 pause together and unpause in either order (the host applies once at the start and once at the end); P3 pauses and P2 leaves (the pause stays until P3 unpauses); P3 pauses and leaves (the others resume; watch the first world tick after the leave, finding F1 of the research); the host pauses and quits (the guests resume through session lost).

### Join admission (N1)
- The host's setup_request type 0 handler 0x831CA0 keeps one joiner: `[0x2528D1C]` the pending member, its address block at 0x212FD70..0x212FD94, `[0x2528CF3]` the answer deferred until the mission ends, `[0x2528D14]` the accept dialog, `[0x2528D18]` the host wait dialog, `[0x2528C40]` the friends query callback 0x831C40. A second request overwrote all of it (the first joiner was never answered and waited for its own 60 s), and 0x8329B0 (the only caller: the member left callback 0x8CB2CE, for any leaver) closed the open admission with nobody answered. With 4 slots and M6 force join launching guests together, overlap is likely.
- N1a (hook 0x831CA0): while an admission is open (pending member set, and the accept dialog, the deferred answer or the friends query running) a request from another member is queued with its request byte, the byte is consumed, and the joiner gets the game's own wait answer (setup_response 0x19, type 0, code 2; built by hand, because 0x831540 with code 2 would open the host's wait dialog again). That answer clears the joiner's deadline. N1b (call 0x8CB2CE): the leaver is dropped from the queue and 0x8329B0 runs only when the leaver is the pending member (or none is). N1c (hook 0x8CB490, the co-op tick): once no admission is open the next queued member that still is in the session goes through the game's own handler as if its request had just arrived. `trace=1`: `admission: member ... waits, member ... is being admitted`, `... is admitted now`.
- Live test: two guests join within a few seconds: each gets exactly one wait answer (code 2) and then its own accept (code 0 or 1).

## Force join (milestone 6)
Spec and probes: `coop-scratch\sr2\M6_FORCE_JOIN.md`, sites `m6_patch_sites.tsv`. Only the front end tick (0x73DCB0) is hooked; the game's own co-op browser does the rest. The first bytes of the six sites are also part of the start-up build check (`code_check`).
- The launcher (`NativeJoin.cs`, profile `sessionKind` `rendezvous`) writes `coop\sr2_join.txt`: `role=host|guest`, `token=<Steam lobby id>`, `password=<9 digits from lobby data cf_join_pw>`, and the optional `name=<UTF-8>` (the player's Steam name, see "Player names"). The adapter follows it by last write time (every 60 ticks); no file or no valid role/token/password = nothing happens. T4 (`trace=1`) logs the join_req's password length, not a name: the first field of the join_req is the password.
- Host, every front end tick: `[0x212AA08]` (online_name) gets ` cfv<VVV>-<digest>-<token>` (older tags dropped, cut to 63 bytes, the tag whole), `[0xE97310]` = 0 (public, else QR2 never lists the session), `[0x212AA88]` = the password. Status `advertising`; in a session a thread writes `in_session N` (the tick does not run there).
- Guest: the front end must be free (no start request `[0x144E75C]`, no pending game `[0xEB2230]`, no dialog `[0x2528D20]`, no session) and logged in (`[0x2529334]` = 4; else 0x80A150 twice, 30 s apart, then status `login_needed`). It writes `cfv<VVV>-<digest>-<token>` into the browser filter `[0x212A9C8]`, `[0x212A980]` = 0, `[0x2528BC4]` = 1 and calls 0x827620; every tick it walks the browser entries (module type 4 in the ring `[0x252933C]`, `+0x3C`, next `+0x98`), reads `online_name` with 0x8E4960 and takes the first listed entry (`+0x65`) that holds the tag. Then `[0x212AA48]` = the password, entry `+0x8E` = 0, `[0x2528D91]` = 0 and 0x73E5A0 with EAX = the index among the listed entries. The load/create dialog is the player's.
- A query ends when it is done, errors, or after 12 s; the next one starts 5 s later (no cap). A join that ends at the idle front end for 10 s is a failed attempt; the third gives up (0x827540, filter cleared) until the join file is rewritten.
- Status (`coop\sr2_status.txt`, `state=<s> detail=<d>`): `advertising`, `in_session N`, `waiting`, `login_needed`, `searching N`, `found`, `dialog`, `joining`, `joined`, `failed`, `stopped`. The launcher publishes it as lobby member data `cf_status`.
- `trace=1` logs every step (`force join:` lines). Live probes still open: spec section 9 (1 to 9).

## Player names (milestone 12)
Spec: `coop-scratch\sr2\M12_PAUSE.md`. Each player shows the Steam name, not the saved LAN or online name.
- The game builds the local member's name in one function, 0x80A070 (cdecl(cap), edi = a wide destination, cap limited to 0x40 wide characters, AL = 1 on return; entry bytes `83 EC 44 A1 50 0B E8 00`). It copies the LAN name (`[0x2528BC4]` = 0, `char[0x40]` at 0x212AB08) or the online nick (1, 0x212AB48), converts with mbstowcs and terminates. Callers: 0x80CAF1 (the host's local member +0x4C), 0x80DB1E (the guest's, then +0xCC through the filter), the 0x82 notice text, the net info dump. The join_req carries the wide name; the host copies it to the new member (+0x4C, filtered copy +0xCC, which the leave HUD line prints). Both buffers are saved to `settings.dat` (the online nick is the GameSpy login), so they are never written.
- `player_name.cpp` hooks 0x80A070 (MinHook, 8 checked bytes, installed at any `max_players`). With a launcher name it writes it to edi as UTF-16, cut to `min(cap, 0x40) - 1` characters, terminated, and returns 1; without one it calls the original. A byte mismatch logs `player name: site differs, game names kept`. State behind a mutex (the join file is read on the front end thread, the builder runs on the game thread).
- Channel: the join file's `name=` line (docs/CONTRACT.md "Join file"), read by `force_join::onRequestChanged` (`player_name::set`). The adapter rejects the whole name if a code point is outside printable ASCII and U+00A1..U+00FF, or it has more than 15 characters (`player_name_rules.h`); an absent, empty or rejected name keeps the game's own, which is also what a native game started without the launcher does. `max_players` 2 behaves as shipped unless a name is given.
- Launcher (`PlayerName.cs`): the lobby member's Steam name with the same set (other code points `?`, controls dropped, trimmed), cut to 15 characters. Members with equal shaped names (case-insensitive) get ` 2`, ` 3` ... in ascending Steam id order, the first keeps the name, and the base is cut so the whole stays within 15; the game denies a join whose name is already in the session (reason 2, 0x815F7F, probably system link only). 15 is the console UI's gamertag length; the buffer allows 63 (unverified: the scoreboard and HUD).
- Trace: always `player name: launcher name "<utf8>"` or `player name: none from the launcher, game name kept` once per change (and `player name: the launcher's name is outside the allowed set or too long, game name kept`); `trace=1`: `trace: name: local member named "<name>" (launcher|game)` per call, the game's name read after the original.
- Live test: three players with distinct Steam names see each other's names on the scoreboard and in the leave HUD line; two accounts with the same persona join without reason 2; a native game started without the launcher keeps its LAN name. One PC: a hand-written join file whose name holds an accented letter shows it on the in-game player list; removing it and restarting gives the game's own name.

## Steam tunnel (milestone 10)
Spec and probes: `coop-scratch\sr2\M10_TUNNEL.md`. Ini key `transport=steam|native` (`coop\sr2_adapter.ini`, read once at start; native is the default and the answer to a missing or invalid value, which is logged). The launcher writes the host's choice (profile option `transport`, `host: true`), so a guest never differs from its host.
- The game has one UDP socket (psnet, `[0xE824C0]`, bound once to port 4200), one send (`sendto` at 0xC1B5A2) and one receive (`recvfrom` at 0xC1BDBC) behind two `select` calls (0xC1BD73 in the pump, 0x814375 in the net thread). All gameplay, join and LAN discovery datagrams use it. GameSpy uses its own sockets.
- Steam mode plays the shipped LAN (system link) co-op over a virtual subnet: no login, no OpenSpy, no QR2, no NAT negotiation (the member-added callback 0x811D70 returns early for a LAN session). The host starts co-op from Co-op > LAN (New or Load), not Online; an online session reports `wrong_mode`.
- Sites (`tunnel_sites.h`, every byte read from the exe, checked together at install and written all or nothing): S1 0xC1B5A2, S2 0xC1BD73, S4 0xC1BDBC and S5 0x814375 are call retargets to `tunnel.cpp` (stdcall WinSock signatures, no naked stubs); S3 0xC1BD89 and S6 0x81438A (`__WSAFDIsSet`) and the function entries are only checked; A1 0x810CAF `74 69` becomes `EB 69` (the public address is the private one, also for a logged in player); the five L1 `gethostbyname` calls go to the own address thunk at any `max_players`. A mismatch logs `tunnel: sites differ, steam transport off` and leaves everything native. Native writes none of these (`tunnel: native transport, game sockets untouched`).
- Virtual addresses: `10.a.b.c` from the account id (low 32 bits of the SteamID64): `a` = bits 16..23, `b` = bits 8..15, `c` = 1 + low byte % 254. Port 4200 always. Two members with one address leave the higher SteamID unmapped (`tunnel: steam id X shares virtual address A with Y`). Slots are the launcher's routing key only: the member table (address, SteamID, current slot) is rebuilt from every `NetClient::poll` snapshot, also on every send, and a new epoch or a re-slot changes only the slot.
- Send (S1): destination 255.255.255.255 from the host goes to slot 0xFF, from a guest to the host slot; a member's address goes to its current slot; anything else is dropped and counted (`no_peer`, `not_virtual` logged once per address). Always returns the length. Frame `GAME_DATAGRAM` 0x0100, unreliable, payload `u32 dst` + 1..1300 bytes. Receive: the frames arrive on the link thread (`NetClient` `onFrame`), are accepted when they are 5..1304 bytes, addressed to our address or broadcast, from a slot with an address, and wait in a 256 datagram inbox (oldest dropped, counted `inbox_full`). Select answers "readable" from the inbox (auto-reset event for the 0 and 10 ms waits, the real socket is never polled); recvfrom pops one and reports the sender as its virtual address at port 4200, an empty inbox is WSAEWOULDBLOCK. Counters are logged every 5 s while they change (`tunnel: sent N received M dropped ...`, `large` = datagrams over 1150 bytes).
- Own address: WELCOME ends with the local SteamID (`SessionSnapshot::localSteamId`); the five L1 calls overwrite the first entry of the own name's address list with `10.a.b.c` (`lan_address_rules::putVirtual`; before WELCOME nothing changes and `tunnel: own address asked before the launcher link` is logged once). `tunnel: own address 10.a.b.c` at the first WELCOME.
- Retired in steam mode: E1..E3 and H1/H2 (`game_port` is ignored and logged), the L1 adapter rule, the M8 browser tag and the force join password (only lobby members reach the host). Still installed: D1, G1, T11, the milestone 5 to 9 logic.
- Version gate: trailer flags bit 1 = steam transport, so a native and a steam build refuse each other (no protocol version bump).
- `SIO_UDP_CONNRESET` off on the game socket in both modes (`game_socket.cpp`, a thread waits for `[0x252A608]` = 1): `game socket: connection reset reports off`.
- Force join in steam mode: the host only sets `[0xE97310]` = 0 each front end tick (no name token, no password; `wrong_mode` for an online session). The guest waits for the link and the host's PEER_UP and a free front end, calls 0x7EE710 (LAN search), takes the first entry of the list `[0x2528BF4]` (next +0x4B8, server id = low byte of +0x4B4, address +0x45C in network order), requires that address to be the host's virtual address (else `failed host_address`, both addresses logged), clears `[0x2528D91]` and calls 0x813160(id); 0x7EE730 stops the search once after the load dialog or the join. Statuses: `waiting`, `searching N`, `found`, `dialog`, `joining`, `joined`, `failed`. The precondition "the front end stack holds state 2" is not checked separately: the hooked front end tick (F1) only runs in state 2.
- Launcher: `games/sr2.json` has port 27962, the `transport` host option and `bridgeWhen`; with `transport=steam` the launcher builds the bridge and the session inside the rendezvous session (NativeJoin as before), WELCOME ends with the local SteamID (the local test transport reports its UDP port), and GAME_DATAGRAM is relayed unchanged (`docs/CONTRACT.md`, "Game messages of the SR2 adapter").
- Tests without the game: `ctest` (`tunnel_rules_test`, `tunnel_sites_test`, `lan_address_test`, `guest_join_rules_test`, `config_test`, `trailer_rules_test`, `game_port_test`, `join_deny_rules_test`), `python tools/sr2/tunnel_launcher_test.py` (two launchers, fake adapters) and `python tools/sr2/tunnel_adapter_test.py` (the real tunnel code through `tests/tunnel_standin.cpp` against `tools/sr2/fake_launcher.py`: the guest's broadcast ping, the host receiving it from the peer's virtual address and answering with a broadcast pong, the guest's join request to the host's address).
- Not verified (live gates): the host's address field in the pong info (R2), pong flag bit 9, LAN Load keeping join type 1, 3 to 4 players on a LAN session (R1), datagrams near 1300 bytes through Steam's fragmentation (R3, the `large` counter), added latency (R4), DLC parity (R5), the LAN name (R6), the S5 rewrite while the net thread runs (R8).
