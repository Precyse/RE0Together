# CODEMAP: dd2

Dragon's Dogma 2: the REFramework C++ plugin. Built: phase 1 of the design (`coop-scratch\dd2\design\phases.md`), the
world gate, the owner half of the body streams, the shared world clock, forced offline play, the look card, peer puppets,
the guest's save redirect, the co-op profile (capture in solo play, splice at a co-op load) and the enemy sync (host enemies mirrored on the guest, guest hits replayed on the host) (built, not live-tested). Index and "where to look for X": `CODEMAP.md`.

## adapters/dd2/ (C++20, x64, `reframework\plugins\dd2coop.dll`)

Build (VsDevCmd `-arch=amd64`): `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build`; the DLL is
copied to `adapters/dd2/dd2coop.dll`. Unit tests: `ctest --test-dir build`. Needs REFramework (dinput8.dll) in the game
folder; uses the launcher link, logging and crash dumps of `adapters/re0/src` and `adapters/common`.

## RE notes

`TimeManager.setTime` 0x145a7fdc0 (the dump has no parameter names). Decompile `coop-scratch/dd2/decomp/funcs/145a7d7d0.c`: the order is (hour, minute, day, weather immediately).
- The body compares `DAT_14e2f2664 * param_3 + DAT_14e2f2668 * param_4` with the elapsed day seconds float (`TimeData+0x40`); `14001ee30` computes the hour as `seconds / DAT_14e2f2664` and the minute as `seconds / DAT_14e2f2668 % 60`, so 0x...2664 is the hour length and 0x...2668 the minute length: param_3 is the hour, param_4 the minute.
- The callee `TimeData::setDayTime(hour, minute, day)` returns at once for `hour > 23` or `minute > 59`, and takes param_5 as a day when it is not negative: `day % DAT_14e2f2628 (28)` is compared with it and the day counter is rebuilt as `(current - current % 28) + param_5` when param_5 is below the current day, else set to param_5 (capped at DAT_14e2f2630 = 1,000,000). So the third value is an absolute day only going forward; a day behind the guest's is not reachable, and -1 leaves the day alone.
- param_6 true calls `WeatherManager.setWeatherImmediate`.
- Engine callers confirm it: `146dbd260` calls setTime(mgr, 5|7|19|21, 0, -1, 1) (the time-of-day skips), `1473572d0` setTime(mgr, 0, 0, day, 1) (skip to a day).
World_clock passes (hour, minute, day or -1 when the host's day is behind, true).

### Title load (the forced load without the menu)
`title_load.cpp` calls `app.MainFlowManager.requestStartType(StartType)` 0x145b3cc60 (calls.h `kRequestStartType`, verified with `tools/dd2/verify_rows.py`) with `StartType.Latest` (literal read at run time; from the type database NewGame 0, InitNewGame 1, Latest 2, Base 3, BackLatest 4, BackBase 5, BackStart 6, RedoNewGame 7, RedoNewGameSkip 8, SystemMenuSave 9, ExitGame 10, Restart 11, NRDEnding 12). Evidence, `coop-scratch/dd2/decomp/funcs`:
- `ui030201.setFlowId` 0x1418c5640 (`1418c1a60.c`) ends its Start branch with `GuiManager.requestGuiType(-1)`, `MainFlowManager.requestStartType(this.Start)` (line 2404, `*(param_2 + 0x214)` = `Start`) and `GUIBase.setUpdateDrawSelf(this, false)`. `requestStartType` has that one direct caller; the UI part before it is only fade handling and the preview-model clear. The menu's Continue row (`onSelectList` case Latest) sets `AfterCheckStartType = getLatestStartType()` and the CheckValidSave flow, which later runs this tail.
- `getLatestStartType` 0x1450547d0 (`1450536c0.c`) maps the newest save kind to a StartType: auto-save slot -> 2 (Latest), manual -> 3 (Base) or 5, back-start -> 6, clear -> 7, add-auto -> 9. Latest is the auto-save kind, so a guest's Continue is `requestStartType(2)`.
- `requestStartType` (`145b3cc60.c`): fades in if no fade is up, `TimeManager.initTimeData`, `MainFlowManager.resetManager`; for 2, 4 and 12 it sets `ContinueSlot` (+0x12c, tdb field `ContinueSlot` 300) = `GameSystem.UnitNumber (+0x120) * 5` and calls `changeFlowPhase(15)` (RequestLoadData). Types 3, 5, 6, 7, 8, 9 call `requestLoadingUI` and `requestLoadGameData(unit*5 + k)` themselves.
- `changeFlowPhase` 0x141050050 (`14104f4e0.c`) case 0xf (RequestLoadData): `GuiManager.setupLoadingUI`, `GuiManager.requestGuiType(1)` (replaces the title GUI type 10 that phase 8 requested: this is what takes the title off the screen), fade handling, then `requestLoadGameData(this.ContinueSlot)` 0x145b3cf20.
- `requestLoadGameData(slot)` builds the closure `MainFlowManager.<>c__DisplayClass217_0` (this, slot at +0x28, slot type at +0x2c from `GameSystem.getSaveSlotType`), a `SaveLoadRequestArgs` (`.ctor` 0x140de5770) with callbacks (`b__1` / `b__3` success: `changeFlowPhase(0x14)` RequestLoad; `b__6` / `b__7` result and process-result handlers that run the error callback lists on a nonzero result: RequestLoadDataError 16, LoadDataError 17 / 18) and calls `SaveDataManager.requestLoad(slot, args)` 0x145c92980, the hooked funnel of load_slot.cpp. So `requestStartType` -> `changeFlowPhase(15)` -> `requestLoadGameData` -> `requestLoad(slot, args, ...)`, and the guest's slot is rewritten in the hook.
- Phase enum (tdb order): 8 TitleMenu (`changeFlowPhase` case 8 requests GUI type 10, the title), 11 InitLoadRequest ... 15 RequestLoadData, 16 RequestLoadDataError, 17 LoadDataError, 18 LoadDataError0014, 20 RequestLoad, 27 InGame. The rule reads phases by name from `world_gate::phase()`.
- Earliest state: `MainFlowManager` in TitleMenu (`get_IsTitleMenuPhase` 0x147019850 = phase field +0x13c == 8). The title GUI's `FlowNow` (`ui030201.FlowId`: 1 ConvertSaveData, 2 WaitApplyUnitNo, 3 Wait, 4 In, 5 Title, 6 to 9 the extra contents prepare and check, 10 PreSelectMenu, 11 SelectMenu) is read by the update hook. `update` 0x145050fe0 handles flow 5 (Title) by waiting for a key or mouse (`IsAnyTrgKeyboardMouse`) before flow 6. The gate takes Title (the press-any-button wait) or SelectMenu: save conversion and the unit number (flows 1 and 2) are done, nothing of the GUI is mid-transition, and no input is needed. The extra contents prepare and check (flows 6 to 9, after the key) are skipped by this route; the game's own skip-title boot path (onUpdate phases 9, 10, 11 then 15) runs `ExtraContentsManager.requestCheckExtraContents` in MainFlow phase 10 instead (open: whether DLC content is complete after a guest's load).

### Title menu (guard: New Game)
The title menu is the GUI `app.ui030201` (rows: `ui030201.ListInfo`, `ItemType` of the enum `ListItemType`, literals read at run time; from the decompile `Invalid` is -1, NewGame 0, InitGame 1, AutoSave 2, ManualSave 3, BackStart 4, Option 8, Exit 9, Store 10, SelectSaveData 11, LoadOtherGame 12, Latest 13 (Continue)). Evidence, `coop-scratch/dd2/decomp/funcs`:
- `ui030201.onSelectList` 0x146089cd0 (share 1, hooked; `146087170.c`): the only place a row is chosen, called from `update` 0x145050fe0. It reads the selected row (`ScrollCtrlBase.get_SelectedInfo` 0x14640f3d0, calls.h `kTitleListSelected`; a shared body, called, never hooked) and switches on `ListInfo.ItemType` (+0x38): case 0 NewGame sets flow 0x21 then `setFlowId` (new game confirm); cases 8, 9, 10 flows 25, 26, 28 (Option, ExitConfirm, Store); cases 2, 3 (the Load rows) flows 0xC, 0x14 or 0x1E; case 13 Latest sets AfterCheckFlow 0x16 (FadeOut), AfterCheckStartType = `getLatestStartType()` and flow 0x1D (CheckValidSave). Fields are read through REFramework by name (`ListCtrl`, `ItemType`), not by dump offsets.
- `ui030201.update` also calls `SaveDataManager.requestLoad` itself, for the slots 0 to 14 in flow ConvertSaveData (1, `updateUnitDataList` per unit, while its convert flag is set): a guest's rewrite sends those to the forced slot too (not seen in a live run).
- `SaveDataManager.requestLoad(slot, args, ids)` 0x145c92980: the slot (param_3) is stored in the queued Request at +0x24 and the args object is separate, so rewriting the Int32 argument in the pre-hook is the whole change.
